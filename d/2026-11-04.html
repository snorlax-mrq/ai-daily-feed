    Scaling Git at OpenAI

    How OpenAI built Pando, a Git-compatible backend designed for the scale of development that Codex makes possible.

    • 因 Codex 讓開發併發量暴增，OpenAI 的 monorepo 去年底開始出現抓取與推送緩慢、合併失敗，可靠性一度跌破 90%，於是自研 Git 後端 Pando，且不改工程師既有的 Git 工作流。
    • 兩個關鍵取捨：放棄全庫級一致性、改採因果一致性（每個 ref 各自序列化，不同分支的推送不再互相排隊），以及不再為每個客戶端各自產生 packfile、改為重用同一份 pack。
    • 推送時把 pack 直接串流進物件儲存、用一次解碼驗證，再以多鍵交易寫入 ref 版本，整個寫入只需常數次 metadata 讀寫；讀取時以 packfile-uri 讓客戶端自行下載多個 pack，相關改進也回饋上游 Git。
    • 成效：推送中位延遲降低近 80%，每天可送達近 1 PB Git 資料，單一小時曾送出 57 TB、超過 99% 來自本地快取，且只需少量 CPU 核心。
    • Pando 本身是用 Codex 在 10 週內從零到上線：核心由一位工程師設計、由代理團隊實作，並用 GPT-6 Astra 寫 Lean 與 TLA+ 形式化規格來找 bug。

    Cost per task: Using cheap classifiers to route across Gemini models and thinking levels

    Per-token API prices keep falling, yet engineering bills for autonomous coding agents keep climbing....

    • Google 開發者部落格指出，token 單價持續下降，但自主編碼代理的工程帳單持續上升；真正該看的指標是每成功任務成本，也就是把所有迴圈、工具呼叫、重試與思考的總花費除以通過驗證的任務數。
    • 解法是在昂貴推理模型前面加一層便宜的分類器路由：日常決策先用輕量模型判斷，只有難題才升級到高思考等級的模型。
    • 示範用 TypeSafe 的 Jev（結構化輸出分類器，單次前向就能回答 Choice、Score 或 Noul 機率）做路由；文章特別聲明 Google 與 TypeSafe 沒有合作、不是背書，同樣模式可用其他分類器實作。
    • 踩坑經驗：用單一「簡單或複雜」的 Choice 問題路由，Jev 幾乎把所有任務都判成簡單，連需要 LRU 快取追蹤或模冪運算的題目也一樣；改成一次問一個原子化的 Noul 判斷才拉開差距。
    • 另一個結論是 regex 與 token 長度這類直覺路由法，在沒見過的代理任務上會失效。
