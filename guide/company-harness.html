30 秒版本

LangChain 在行銷、業務、工程各養一個內部 agent（GTM Agent、OpenSWE、Content Studio），建法相同。原文歸納成五個元件：住在人們工作的地方（Slack）、認得是誰在問並決定用誰的身分、全域與個人兩層記憶、沙箱執碼經代理取憑證、很大比例靠排程或事件觸發。

  • 五個元件其實是五道題：入口、身分、記憶、執碼、觸發。
  • 身分最難：同一 agent 依場景混用 OBO 與固定憑證。
  • 記憶分兩層，原文自認這是探索最少的一塊。

三個 agent、三種工作，卻用同一套建法

先把樣本講清楚。原文說 LangChain 在行銷、業務、工程三個團隊建了內部 agent，然後逐一介紹三個主角：GTM Agent是主動、常駐的業務 agent，會監看並回覆 email、處理新進的合格潛在客戶、送每日簡報、回答帳戶相關問題，也能執行對外開發（outbound）動作；OpenSWE是工程 agent，能動手寫並草擬 PR，也對所有 PR 跑 code review；Content Studio是行銷 agent，能依公司風格與定位知識草擬素材——部落格、圖片、PowerPoint、影片。

關鍵句在這裡：「所有這些 agent 都用同樣的方式建；我們認為這是建 company harness 的通用配方」。原文標題講 company harness，但正文沒有給出定義句——它給的是配方本身，也就是後面五節各處理一個問題的結構（編輯推論：所謂 company harness，指的是公司內部共用、讓多個團隊各自長出 agent 的那層底座）。文章開頭則稱這些 agent「完全改變了這些團隊的工作方式」，範圍限定在行銷、業務、工程這三個團隊。

閱讀前提。這是 LangChain 自家內部 agent 的經驗整理，全文沒有提供導入團隊數、節省工時、使用人數或執行量等量化數據，敘述以定性描述為主；「完全改變了這些團隊的工作方式」是原文對行銷、業務、工程三個團隊的說法，文中未附量測方法或成效數字。文中出現的 Managed Deep Agents、LangSmith Sandboxes 是 LangChain 自家產品，原文即以其為建議實作（另在文末感謝 @caspar_br 協助撰寫）。

五個元件：入口、身分、記憶、沙箱、排程，各自是一道題

原文開頭就把「每個團隊最後都收斂到的核心原語」列成五條。值得注意的是它的寫法：五條全部寫成需求句（住在人們工作的地方、知道是誰在問、有記憶、程式跑在沙箱、很大比例是排程執行），而不是技術選型——先講要滿足什麼，才講用什麼滿足。

入口（Slack）每個 agent 有自己的 Slack app，可被 DM、也可在頻道被 tag；另有「breakout」機制，把插入人類討論的 agent 對話拆到頻道裡的獨立 thread。在頻道裡用，其他人看得到別人怎麼用它；agent 若直接在人類 thread 裡跑，會污染原本的對話。
身分認得是誰在叫用它，並依服務決定代該使用者行動（OBO），或用自己的身分／固定憑證行動。某些工具必須以本人權限執行（如用你的 GitHub handle 開 PR），某些工具則不該要求每個人逐一登入。
記憶兩層：全域記憶套用到所有使用者，個人記憶只套用到特定使用者；由 agent 自己決定哪些事實要記到哪一層。原文自認這是目前探索最少的一塊，還有很多想做的事。
沙箱執碼agent 本身跑在沙箱外，連進沙箱裡執行程式；三個 agent 的 base image 各不相同、相依套件也不同。任務常需要寫並執行程式，而連外服務透過 secret proxy 從沙箱內取用憑證。
排程與事件觸發很大比例的執行是排程或由事件在背景觸發，而不是有人直接叫用；來源有兩種：agent 開發者設定，或使用者要求 agent 自己建 cron。原文稱之為 ambient agents：沒有人在場點名時，agent 仍要自己動起來。

這五者怎麼互相扣著？原文沒談先後順序，而是把它們當同一層平台能力一次給：Managed Deep Agents 建在開源 Deep Agents harness 之上，提供 channels、crons、sandboxes、memory、identity，同時留給團隊改 agent 行為的彈性。拆開看，依賴關係其實很清楚（編輯推論：以下是從原文事實推導，原文未明說）：排程讓 agent 在沒有使用者叫用時仍要行動，於是「這一步用誰的身分」立刻變成必答題——原文正是這樣解釋 OpenSWE：被訊息叫用時代你行動，背景跑 code review 時改用 GitHub app 自己的身分；沙箱執碼必然經過身分與憑證，所以走的是 secret proxy；記憶的兩層切法也與身分的分場景思路一致——把「個人脈絡」與「共用脈絡」分開放（編輯推論）。

身分：原文自稱最棘手的一題，三個 agent 給三個答案

原文直說 identity 是「我們處理過最棘手、最難纏的問題」，核心問句是：agent 採取行動時，是代替誰行動？業界有兩種作法——on-behalf-of（代理叫用它的那位使用者）與固定憑證（不論誰叫用都用同一組憑證，例如 service account）。原文沒有裁決哪一種才對，而是讓三個 agent 各自混用：

OpenSWE：前景代你、背景代自己。你傳訊息給它，它代你行動，例如用你的 GitHub handle 開 PR；它在背景執行時（例如當 code review agent），則以自己的身分（GitHub app）行動。

GTM Agent：靠固定身分省登入，靠本人身分守住敏感工具。Salesforce 之類的工具用固定身分，這樣不必每個人都去登入；email 之類的工具則代叫用者行動，而且這些工具只在 DM 開放，在共用頻道裡不提供。

Content Studio：公司帳號用固定憑證，但加上白名單。Notion 之類的工具代叫用者行動；Twitter 則用固定憑證（公司帳號），但只有白名單上的使用者能叫用某些操作——不是每個人都能發文，其他人可能只能讀或先寫草稿。

把這三段並排，會看到同一個模式：同一個 agent，對不同的人開放不同的能力，界線畫在「工具 × 場景」上而不是 agent 層級上。GTM Agent 的 email 工具在 DM 開、在頻道關；Content Studio 的發文權限按人名開放；OpenSWE 則按「有沒有真的有人在叫用」切換身分。這也解釋了原文那條元件為什麼寫成兩件事——「知道是誰在問」加上「代他行動或用自己的身分」（編輯推論）。

記憶、沙箱、排程：兩層記憶、憑證留在沙箱外、誰按下開始

記憶：只有兩層，而且承認還很粗。所有 agent 都有兩層記憶——全域記憶套用到所有使用者、個人記憶只套用到特定使用者，由 agent 自己決定哪些事實寫進哪一層。原文對這塊的評語很直接：這大概是目前探索最少的一塊，我們還有很多工作要做。

沙箱：agent 在外、程式在內，憑證留在沙箱外。三個 agent 都能寫並執行程式，共同模式是 agent 跑在沙箱外、連進沙箱裡執行；三者的 base image 與相依套件各不相同，其中 OpenSWE 會依頻道／使用者判斷該起哪一個 base image。連外服務走 LangSmith Sandboxes 上的 secret proxy，讓 agent 從沙箱內部取用憑證（編輯推論：原文正文只說「三個 agent 都採用了 secret proxy」，金鑰不進沙箱一說依原圖「No keys inside」標示）。

排程：誰來按下開始，有兩種答案。很大比例的執行是排程或事件在背景觸發，而非使用者直接叫用。有些由 agent 開發者設定——OpenSWE 監聽 PR，一有新 PR 就去審；有些由使用者當場要求——作者請 GTM Agent 每天送簡報，它就自己建了一個 cron。原文用「ambient agents」稱呼這種狀態：agent 不只是被叫才動的工具，而是持續在背景做事的角色。

帶走三件事

五個元件其實是五個介面決策，不是五個技術選項。入口在哪（Slack，加上非同步量大時的自建 UI）、用誰的身分、記到哪一層、程式在哪跑、誰觸發——原文的「通用配方」全寫成需求句，先回答要滿足什麼，才輪到用什麼框架滿足。

身分要能分場景，這是「多團隊共用」的真正門檻。OpenSWE 前景代你、背景代自己；GTM 的 email 工具只在 DM 開；Content Studio 的發文權限按白名單開放——同一個 agent 對不同人給不同能力，界線畫在工具與場景的組合上，而不是把 agent 切成好幾支（編輯推論）。

排程把 agent 從工具變成同事，也把所有難題逼出來。很大比例的執行沒有人在場，於是「誰的身分」「哪一層記憶」「憑證怎麼進沙箱」都必須在無人叫用時仍成立（編輯推論：這正是原文把五者打包成同一層平台、而不是留給各團隊各自解的理由）。
