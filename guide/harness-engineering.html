這篇不是 prompt 技巧集：它把「交件、證據、進度」三件事先寫進流程，再讓模型在流程裡跑。

原文先給定義——harness 協調模型周邊的指令、工具、權限、狀態與檢查。七層不是抽象架構，是七個可以動手的地方，示範用文件工作流：來源放 sources/、草稿放 drafts/、定稿放 published/。

分界線是「跨任務」與「單次任務」，不是重要程度

根目錄 CLAUDE.md 只放長期有效的事：輸出路徑、來源要求、寫作慣例。臨時截止日、還沒解決的來源疑問跟著那一次任務走。

原文順手拆了一個常見誤解：用 @path 拆大檔只是整理用，import 進來的內容在 session 開始時一樣全部進 context；偶發才用的流程放 skill，那才是真的省。

第二層的判斷標準很實用：每一步都要有可觀測的結果。讀資料→交出選定的來源；寫稿→存成檔案；審查→交出作者能處理的 finding。「檢查正確性」這種步驟把太多判斷留空。

一輪跑完，誰把球傳給誰

第三層的驗收方式很樸素：先抓一頁已知的頁面，確認內容對得上，再讓長流程依賴它；抓取失敗時留下文件識別碼與失敗原因，別重複同一個請求。

沒角色的伺服器就從 /mcp 關掉；原文只給這個動作，沒給省下多少 context 的數字。

第五層最值得抄：reviewer 拿讀取與搜尋工具，不拿修改權。判「錯」必須附衝突證據與可套用的修正；判「未解」要指出缺哪份證據。

原文補了一句很容易被忽略的話：一份自信的審查報告，背後仍要有可用的證據。所以驗收看的是環境裡留下的成品，不是對話有多漂亮。

恢復手段要分清楚：/rewind 只還原被追蹤的檔案編輯，shell 的改動與多數 subagent 的編輯要另外回收，版本控制才是耐久紀錄。

哪幾條站得住：機制事實、作者配置、該打折的主張

先把三類分開，再決定要不要抄：① 對得上官方文件的功能行為；② 作者的配置選擇；③ 需要打折的通則。

那條 60% 是全文最該打折的地方，也是原文自己打折的地方：它引的是 Anthropic 早期試用者報告，接著明講「屬於那個模型實驗」，省多少要用自己完成的任務量出來。

量測方式原文也給了：用 /usage 看回報用量、/context 看什麼佔住視窗，把委派的審查與重試算進同一個任務，再記下你花多少時間複核、成品被退回幾次。

第六層的寫法值得單獨學：寫一句「請深入思考」不會改變已設定的 effort，要改的是設定本身；而且換設定時只動一個元件、重跑同一個任務、同時看成品與證據。

閱讀前提。這是個人配置教學，非 Anthropic 官方文件；七層的落點都對得上 Claude Code 既有功能，但設定細節以你家版本的文件為準。原文的程式碼片段以截圖呈現，本導讀只轉寫文字描述的部分，未轉抄設定內容。

立場與查證。原文結尾有 Substack 與 Telegram 導流，屬個人品牌經營。分類中的「① 機制」是原文對官方文件的援引，本站未逐條複驗官方文件。

帶走三件事

先寫驗收再開跑。草稿、檢查表、進度筆記，是長任務唯一的下限。

審查要能指回來源。給 reviewer 讀取權而非修改權，它才不會改掉證據。

七層是配置，不是門檻。先挑一層動一個元件，重跑同一任務再比較。
