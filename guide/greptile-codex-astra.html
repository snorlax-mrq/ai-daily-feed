Greptile 做的是「帶著整個 codebase 脈絡」審查並測試程式碼變更的 AI agent；這篇客戶案例講的是它把驗證從讀 code 延伸到真的把應用跑起來。

原文直說：四道驗證裡有一部分非得把應用跑起來不可——「reading the code alone might not reveal the problem」。

為什麼不找人測？Gupta 的說法：「A QA firm testing all of your changes is just impractically slow considering how fast we're able to ship code with these models.」人工 QA 跟不上出貨速度，應用測試才需要自動化到規模。

讀 code 與跑起來，各看到什麼

原文沒說哪幾道驗證非得跑起來，只給了一個例子（Greptile 執行長的舉例）；右欄目前也就只有這一個案例。

→ 可橫向滑動

本頁數字與客戶規模均出自 Greptile／OpenAI 說法（自報），原文未附方法論或第三方驗證。

Knowledge Base 把 codebase 索引成人與 agent 都讀得懂的文件，透過 MCP（Model Context Protocol）server 給 Codex，Codex 寫出的程式就會跟著客戶既有模式走。

成效怎麼量：團隊追蹤 AI 產生程式碼被 revert 的頻率——「When we provide agents with context, fewer reverts happen and customers save time and save inference.」省下的時間與 inference 可以轉投新工作。

Greptile 自己也是重度用戶。「We are massive users of Codex」——每個職能都有大量用量，工程部門尤甚；Ultrafast 的長期目標，是讓改動與發布關鍵企業軟體像發 side project 一樣簡單。

帶走三件事

能跑就先跑。有些 bug 讀 diff 看不出來，只有執行才現形。

脈絡是可量測的投資。用 revert 率當尺，原文未給改善幅度。

三個名詞份量不同。應用測試有例子，Daybreak 只有定位。
