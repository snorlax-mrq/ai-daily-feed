代理把算力重心推回 CPU，也把「每瓦能養幾個代理」變成採購規格。

代理不只生成答案。它會搜尋資訊、查資料庫、寫並測試程式，然後真的採取行動。

原文的關鍵句是：這些步驟每一個都依賴 CPU，代理在任務中不斷在兩種晶片之間切換。

（編輯推論：這也解釋為什麼「模型更快」不一定讓代理更快——慢常常慢在半路的工具呼叫，不在生成。）

代理越自主，工具呼叫就越密：每次搜尋、每次跑測試，都是一次 CPU 排隊。

於是「能同時養幾個代理」變成容量問題，而容量在資料中心裡最終換算成瓦數。

電力上限，把「每瓦」推到規格欄

原文用 power limited 形容 AI 工廠：電力有上限，所以營運方只能挑「每瓦做最多事」的基礎設施。

需求寫得很清楚：更多代理同時跑，但每一個都不該等更久。

指標數字對比對象
每瓦代理數1.6 倍最快的 x86 CPU
代理速度2 倍最省電的 x86 CPU
100MW 比較結論單顆勝過兩者同上兩個 x86 基準（NVIDIA 測）

兩個倍數不是同一場比賽：一個比「單位電力能塞幾個代理」，一個比「單一代理跑多快」。

（編輯推論：原文把它們並列，是主張兩頭都贏；讀者要自己記住對照的是不同對手。）

那個 100MW 是資料中心規模的推論，不是單機跑分——原文用整座機房的電力預算當分母。

Vera 的定位因此是把「快」與「密」兩種 x86 需求收進同一顆 CPU，業者不必再靠配比抓平衡。

Modal每核沙箱吞吐最高 2 倍，負載重時增益更大

六個數字分散在編碼、編排、資料庫查詢與沙箱開機，不能加總成一個「快幾倍」。

性質也不同：ClickHouse 與 DuckLabs 量的是查詢，Daytona 量的是開機與併發，Perplexity 量的是編碼任務。

唯一由 NVIDIA 自己跑的是 100MW 那一組；其餘都是夥伴自家部落格發布。

原文沒給對手 x86 的型號（DuckLabs 那組以 Intel Xeon 6 為基線）與基準日，也沒說測試方法。

Perplexity 那條還帶著下一步：原文說它計畫在即將上線的生產系統部署 Vera，不只停在測試。

怎麼讀這組數字

先看自己的瓶頸在哪：如果你的代理大半時間在等 API 或等人核准，換 CPU 不會救你。

沙箱開機 10.8 秒對 88.4 秒很漂亮，但它是一次性開銷，占整體迴圈的比例取決於任務長度。

（編輯推論：真正該問的是「同一批代理腳本，換平台後總完成時間變多少」，而原文沒有這個數字。）

第二個問題是基準：against the fastest x86 與 against the most energy-efficient x86 是兩個不同的對手，不能互相代換。

兩個基準服務的讀者也不一樣：在意延遲的買「快」，在意機櫃與電費的買「每瓦代理數」。

（編輯觀點：硬體發布把兩種對手並列很常見，因為兩邊都贏聽起來最強；讀者要自己拆回兩張表。）

第三個問題是誰在測：六家夥伴的數字都掛在自己部落格，動機與方法不透明，原文只把它們當旁證。

帶走三件事

代理讓 CPU 回到預算表。每一步工具呼叫都要有人執行。

電力上限是新的選型軸。比快不夠，要比每瓦養幾個代理。

六個倍數不能相加。先確認對手與工作負載再比。
