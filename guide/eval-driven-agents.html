Eval 驅動開發：平均分會騙人，考卷要先寫

100%收窄 create_ticket 的工具描述後，全部範例通過；原文限定是「小資料集」上的滿分（原文敘述，無第三方驗證）
5 項原文文末列五個常見錯誤，含「信一個沒校準過的 judge」與「加你不需要的 eval」

EDD 是代理版的 TDD：先把「什麼叫好」寫成判得出通過或不通過的考卷，再改代理，每次改動都跟上一版實驗比。

原文的起點很普通：寫 prompt、手動問幾題、調整、再問一次。錯誤明顯時這招夠用，改動一多就分不清最新一版是變好還是變壞。

代理不是程式：同一個問題每次答案可能不同、兩種措辭都算對，它還會自己挑步驟——叫了多餘的工具或漏掉該用的，答案照樣對。

所以測試要換形狀。eval 是在一組範例上替每次 run 打分，可以只評過程，也能讓另一個 LLM 當裁判（LLM-as-a-judge）。

「一次只做一個行為」是方法的前提：目標窄，改動的效果才不會互相污染，hill-climbing 也才有方向。

（編輯觀點：三步中最反直覺的是第二步。eval 要在工具寫好之前就存在，而且當下必須是失敗的。）

規格四欄：先寫會失敗的考卷

原文的短規格有四欄，含糊的「回答有幫助」不算規格——它判不出通過或不通過。

規格欄位docs agent 的寫法判分時看什麼
何時使用者回報東西壞了，如「筆電連不上 VPN」決定範例怎麼挑，不進評分程式
該做呼叫 create_tickettool call 裡有沒有出現它
不該做how-to 問題不開單，如「VPN 要怎麼連」同一項檢查的反面
不能破壞search_docs 與 web_search 仍接住目前處理的問題原本通過的案例是否仍通過

表格為本站整理；第二欄改寫自原文 docs agent 規格，第三欄依原文「用 code eval 檢查是否呼叫參考輸出裡的工具」整理，原文未給此表格。

範例裡的 create_ticket 還沒做，考卷照樣先寫：規則寫在功能之前，才不會照著已完成的輸出出題。

資料集優先用真實 run——使用者的措辭猜不到，邊角也在裡面。原文說少量範例就能起步；沒有 run 就手寫，或請 LLM 把現有範例改寫成更生氣的語氣。

評分器按判法分：判得死的用 code eval，判不死的用 LLM 裁判。docs agent 只問一件事——有沒有叫對工具，所以一段程式就夠。

代理變複雜後要改看終態。coding agent 的成果是它留在系統裡的狀態，每次還得在乾淨環境跑；原文點名開源框架 Harbor（Terminal-Bench 背後的 harness）作為這類 eval 的跑法。

平均分上升的那一次，有一例壞了

接上 create_ticket、重跑同一份 eval：開單類範例由失敗轉為通過，平均分上升，「VPN 要怎麼連」卻從查文件變成開單。

比較要把兩次 experiment 並排：逐例列分數，哪幾例升、哪幾例退一目了然，這是「只看平均」看不出來的。

找原因靠 trace——一次 run 的完整紀錄，含每次模型呼叫與工具呼叫。失敗那筆顯示工具描述寫了「VPN 與筆電問題」，於是所有提到 VPN 的問題都命中。

修法是把描述收窄到「需要 IT 動手」的請求，重跑後全部範例通過。但 100% 不是終點：調校用的就是這批範例，容易過擬合。

檢查方式是留一組 held-out 範例，迭代時不看。調校組上升、held-out 持平，就是過擬合訊號。

把迴圈接進 CI 與上線後：快的 code check 擋壞 merge，慢的 LLM 評分跑夜間或發版前；pytest 與 Vitest 都能接，eval 跟著 PR 跑。

範例也要切分（dataset splits）：迭代時只跑正在做的行為那批，發版前再跑全集。

生產端再用線上評分器抽樣、標註佇列人工複核、看板追分數與成本延遲，把使用者真正問的問題補回資料集。

judge 也得先校準：對照人工評分，問題問窄，用通過／不通過取代模糊的 1 到 10 分量表。

帶走三件事

先寫會失敗的考卷。修完再補 eval，只會寫出必然通過的題目。

平均分不是驗收標準。逐例看升降，才知道哪個行為被覆寫。

滿分要看 held-out。只在自己調過的題目上進步，就是過擬合。
