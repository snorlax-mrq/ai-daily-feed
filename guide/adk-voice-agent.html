讓語音 agent 不冷場：把「卡住 13 秒」變成「先說一聲」

30 秒版本

文字聊天裡，13 秒的資料庫查詢只是個轉圈圈；語音對話裡，它是 13 秒死寂——使用者以為斷線、直接掛斷。Google 這篇教學用開源 ADK 與 gemini-3.8-live 把慢工具「非阻塞化」：benchmark 銷售報告案例中，把阻塞工具改為串流工具，代理的首字回應從 14.4 秒縮短到 1.2 秒。

  • 問題出在架構不在 prompt：阻塞工具會卡住模型的回合，連「正在處理中」都說不出口。
  • 兩種非阻塞模式：進度有故事就用串流工具（return 改 yield）；等待只是等待就放背景執行。
  • 全程 Python 原生——不用自己寫 WebSocket 事件迴圈去管理非同步工具狀態。

問題：語音的敵人是沉默

標準工具的寫法是 async def 做完工作、回傳單一值。在 Gemini Live API 的雙向語音 session（run_live）裡，執行迴圈會等工具回傳才輪到模型講話——所以 13 秒的銷售資料庫查詢，就是 13 秒的完全靜默。原文點破一個常見誤區：靠 prompt 解不了。你可以在指令裡寫「執行時告訴用戶你在處理」，但模型的回合被卡住等 function response，payload 沒回來它一個字都吐不出。

後端查詢也不可能永遠壓到一秒內——所以解方必須是架構性的：讓代理在慢工具背景執行時，照樣保持對話。

解法：兩種非阻塞模式

ADK 把「讓慢工具不卡對話」變成語言層級的小改動。選哪種模式，判準只有一個：等待的過程有沒有故事可講。

逐步拆解（本站整理）

01盤點

找出語音流程裡所有「做完才回」的工具

它們就是潛在的掛斷點：查詢、RAG、任何外部呼叫。先量死寂有多長，再決定怎麼改。

02選模式

進度有故事 → 串流；等待無聊 → 背景

原文的判準很務實：用戶在乎過程就播報（如報表產生），不在乎就安靜（如純等待），避免為了「有反應」而嘮叨。

03最小改動

三種寫法對應三種需求

串流：AsyncGenerator 逐段 yield；背景 A：單次 yield（完成才回，立即應答）；背景 B：保留標準 coroutine，包 FunctionTool 設 response_scheduling = WHEN_IDLE。

04調行為

instruction 明確規範應答節奏

「先應答、轉述進度、完成才報數字」寫進代理指令——非阻塞架構給了模型說話的空間，規範決定它說什麼。

05量首字

以「首字回應時間」為體驗指標

benchmark 銷售報告工作流（gemini-3.8-live）：阻塞 14.4 秒 → 串流 1.2 秒。語音產品的體感，就差在這裡。

五個關鍵詞

阻塞工具 Blocking tool做完才回傳單一值的標準 async 工具。語音場景中等於整段對話凍結。
串流工具 Streaming toolAsyncGenerator 持續 yield 進度訊息。ADK 自動標 NON_BLOCKING——改動只有一個關鍵字。
response_schedulingFunctionTool 的回應排程選項：WHEN_IDLE（等自然停頓）、INTERRUPT（打斷現句）、SILENT（只入歷史不播報）。想保留標準函式寫法時的非阻塞出口。
run_liveGemini Live API 的雙向語音 session。執行迴圈會等工具回傳——阻塞問題的根源。
首字回應時間代理對同一輪請求開口說第一個字前的等待時間。語音體驗的關鍵指標：14.4s → 1.2s。

帶走三件事

語音 UX 的敵人是沉默。轉圈圈救不了語音——任何「做完才回」的工具都是掛斷點（原文示例中，13 秒就足以讓使用者放棄）。且非阻塞不會讓後端變快：13 秒查詢還是 13 秒，改變的是代理的「在場感」。

非阻塞是架構選擇，不是 prompt 技巧。一個 yield 關鍵字、一個 response_scheduling 設定，比催促模型「記得說話」或硬壓後端延遲都實際。

會說話的等待才播報。串流與背景先二選一，判準是「進度有沒有故事」（兩者還可疊加：串流工具同樣能設 response_scheduling）——別讓代理為了看起來勤勞而嘮叨。
