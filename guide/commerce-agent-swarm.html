Google 把上一篇文章的對話式商務架構圖，做成真的能跑的 HappyDelivery 原型：三層解耦——Ingress（Cloud Run／GKE ＋ Cloud Pub/Sub 收訊息、驗簽章，設計目標 150ms 內回 200、實測約 267–302ms）、Session（Cloud Memorystore Redis 存購物車與偏好）、Agent Swarm（LangGraph ＋ Gemini，Supervisor 用 Flash 路由，Inventory／Transaction 兩個專業代理用 Pro（原文未對 Profile 代理標示模型）。三輪對話完成一筆雜貨訂單，全程約 4,240 token、$0.0061，佔 20.32 美元訂單的 0.030%。

  • webhook 絕不等 LLM：先驗簽章、正規化、丟 Pub/Sub，立刻回 200，避免平台重送造成重複下單。
  • 算術交給確定性工具，模型只負責語言與推理；稅、運費、扣款都在 Python 裡算。
  • 成本靠三件事壓下來：Redis 外置狀態、程式碼吃掉重活、Flash／Pro 分層。

第一層：為什麼要「先回 200，再想事情」

原文點出一個常被忽略的順序問題：消費者訊息不是直接打到你的伺服器，而是先穿過電信與平台生態（WhatsApp Cloud API、Google RCS Business Messaging、Apple Messages for Business、SMS 供應商），最後才落到你的 webhook。而這些平台全部共用同一個契約：非同步 HTTPS POST ＋嚴格的確認時限。

後果很具體：WhatsApp 若沒即時收到 HTTP 200 OK（並通過 X-Hub-Signature-256 的 HMAC-SHA256 驗證），會把投遞標記為失敗並啟動指數退避重試（最長 7 天）——「which can trigger duplicate order deliveries」，也就是同一筆訂單被下兩次。

所以 Layer 1 只做三件事：平台各自的簽章驗證（MetaHmacValidator、RcsJwtValidator、AppleJwsValidator、TwilioHmacValidator）、把 payload 正規化成統一的 CommonMessageEvent（channel／sender_id／text／timestamp）、丟進 Pub/Sub 後立刻回 200。原文的架構目標是 < 150ms 完成握手——後面的 session 查詢與推理完全不在這條關鍵路徑上。

實測與目標要分開讀：原文在 Cloud Run 上連打 5 次 live webhook，回應時間為 266.84ms、301.73ms、300.47ms、295.14ms、298.40ms，其中「Cloud Run 內部直接發 Pub/Sub 的額外開銷約 95ms」——也就是說 < 150ms 是三層設計的架構主張，實測端到端握手落在約 267–302ms。同篇也示範了安全防護：正確簽章回 200 並取得 message ID，被竄改的簽章則立刻以 403 擋下。

第二層：把「逛到一半去搭車」變成可接續的狀態

訊息平台是無狀態的：每則簡訊都是一個孤立事件。要讓對話像人，系統必須在每一輪瞬間重建客戶的完整脈絡，而不是每次重讀好幾天的聊天紀錄。做法是用 Cloud Memorystore（Redis），以驗證過的電話號碼為鍵（session:{phone_number}），存顧客 ID、地址、飲食限制與當前購物車，TTL 設 24 小時。

原文給了三個具體顧客旅程：早上 9 點傳「加一加侖牛奶」就關掉去搭車、下午 2 點再傳「再加麵包和蛋，多少錢？」——系統立刻還原購物車並重算總額；profile 標記 Nut-Free 時，Inventory Agent 推薦零食會自動避開，不必每次重講；付款只放 token 化的 payment_ref，LLM 只看得到「Visa ending in 4242」這種遮罩標籤，卡號不進 prompt、也不進 log。

吞吐單一 Basic Tier、1–5GB 的 Memorystore for Redis 實例即可達 10,000–50,000+ QPS，讀寫延遲低於 1ms。換算成對話：每輪約 2–3 次 Redis 操作，等於每秒 3,000–15,000 個活躍對話輪，才需要 Cluster 分片或讀取副本。
容量一個活躍 session（profile ＋ 購物車 ＋ 偏好）序列化後約 2–5KB。5GB 實例可同時容納超過 100 萬個活躍購物車。
實測延遲在 VPC 內對 live 實例連做 5 次 session 讀取：0.299／0.276／0.305／0.210／0.503ms。平均 0.318ms——原文的結論是這一層「在實務上永遠不會是瓶頸」。

第三層：四個角色，一條狀態機

推理層刻意不用「一個超大 prompt 什麼都做」，而是拆成蜂群：Supervisor（Gemini Flash）當低延遲路由器，判斷意圖後分派；Profile Specialist 取偏好、對新客發一次性安全授權連結；Inventory Specialist（Gemini Pro）綁倉儲工具，查庫存、推薦搭配、改購物車；Transaction Specialist（Gemini Pro）綁付款工具，確定性地算總額並發起扣款。

原文的核心信條是「把算術交給確定性工具」：calculate_cart_totals 在 Python 算小計、8.25% 稅、小計超過 15 美元免運（否則 3.99 美元運費）與總額；模型一旦用自由文字算稅或折扣，就可能出錯。

04端到端

Worker 迴圈串起三層

Pub/Sub worker 拉訊息 → 從 Redis 補齊 session → 跑 swarm.invoke() → 把更新後的購物車寫回 Redis（24 小時 TTL）→ 回傳對外訊息。Trace 顯示 Supervisor 判斷為補貨意圖、交給 inventory，兩次 search_catalog 加一次算總額後結束。

三輪對話的實例很能說明這種分工：第一輪說「牛奶和蛋沒了，週五電影夜加點零食」，代理回已加入全脂牛奶 $4.29 與放牧蛋 $3.99，並依過去電影夜紀錄詢問要不要加 Doritos $4.50 與 Sprite 六罐 $5.99；第二輪「Sprite 換成 Coke Zero」後重算小計 $18.77、稅 $1.55、總額 $20.32；第三輪確認後由 Transaction Agent 發起扣款（execute_stripe_charge，amount_cents=2032），成功後清空 Redis 購物車。

成本帳：為什麼蜂群沒有吃掉毛利

多代理架構最常見的質疑是 token 帳單：把龐大 prompt 與整段對話歷史在每一步重送，很容易吃掉零售毛利。原文用三招把成本壓平：狀態外置到 Redis（只傳當前意圖與購物車摘要，輸入 token 不隨購物車線性成長）、重活交給程式碼（稅、運費、折扣、目錄關鍵字比對、Stripe 扣款都是 Python，0 LLM token）、模型分層（高頻路由走 Gemini Flash，深度推理的庫存推薦與付款收尾才用 Gemini Pro）。

實測結果：整個三輪購物 session 約 4,240 token，以 Gemini Flash $0.15／1M 輸入、$0.60／1M 輸出，Gemini Pro $1.25／1M 輸入、$10.00／1M 輸出的標準價計，成本約 $0.0061（遠低於 1 美分）；放在 $20.32 的雜貨訂單上，只佔 GMV 的 0.030%，相比 2.9% ＋ $0.30 的標準刷卡手續費幾乎可忽略。若再開 Gemini Context Caching（適合大型靜態目錄 schema 與不變的 agent 指令），重複輸入成本可再降 75%，每筆訂單成本可壓到約 $0.0033。

原文自承的代價：「蜂群稅」——跨多次 LLM 呼叫的多代理推理可能要 2–4 秒，為避免使用者覺得對話死掉，worker 會先透過訊息 API 送一句進度提示（例如「Checking our fresh aisles for you… 🛒」）再串流最終結果。這也是全篇最誠實的一段：架構解決了可靠性與成本，延遲得靠 UX 手法補。

帶走三件事

把「不能等」與「可以慢」切乾淨。webhook 只負責驗簽章與排隊，推理全部移到非同步 worker；這一個切法同時解掉三個問題——平台重試導致重複下單、尖峰延遲、以及尖峰延遲；至於多代理推理 2–4 秒的體感，原文另以「進度提示」的 UX 手法補償，不是解耦本身能解。實測 267–302ms 的握手時間要跟 <150ms 的架構目標分開看，別把主張當成果。

模型只做語言，錢與庫存交給程式。8.25% 稅、滿 15 美元免運、Stripe 扣款金額全在 Python 工具裡算，換來的是「0 算術錯誤」與可稽核性；這比要求模型「小心計算」可靠得多，也把最貴的 token 花在真正需要推理的地方。

成本優勢來自狀態設計，不是模型折扣。外置 Redis、程式碼吃重活、Flash／Pro 分層三件事加起來，才讓一筆訂單 0.6 美分的帳成立；反過來說，若把整段對話歷史每次重送，同一個蜂群架構馬上就變成毛利的敵人。
