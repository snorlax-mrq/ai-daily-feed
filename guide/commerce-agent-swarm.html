先回 200，再想事情

原文先回答兩個常見提問：訊息怎麼真的落到第一層？架構能不能支援 WhatsApp 以外的通道？

訊息不會直達你的伺服器：它先穿過電信與平台生態，最後才落到 webhook。

WhatsApp、RCS、Apple Messages、SMS 共用同一個契約——非同步 HTTPS POST 加嚴格的確認時限；payload 與簽章標頭各異，就由 Layer 1 吃掉差異。

沒即時回 200 OK，WhatsApp 會把投遞標成失敗並指數退避重試（最長 7 天）。原文點名後果：可能造成重複下單。

所以 Ingress 只做三件事：驗簽章（四個 validator，涵蓋 HMAC、JWT、JWS）、正規化成 CommonMessageEvent、丟進 Pub/Sub 後回 200。

順序是：先驗簽章、再正規化，任何一關不過就別進佇列。

四個 validator 分別對應 Meta、RCS、Apple 與 Twilio 的簽章格式，可插拔替換。

同篇也示範了護欄：正確簽章回 200 並取得 message ID，被竄改的簽章立刻以 403 擋下。

架構目標是 <150ms。Cloud Run 實測差了將近一倍，其中約 95ms 花在直接發 Pub/Sub——目標與實測要分開讀。

第二層把狀態搬出伺服器：以驗證過的電話號碼為鍵（session:{phone_number}），存顧客 ID、地址、飲食限制與購物車，TTL 24 小時。

原文的容量帳：單一 1–5GB 的 Basic Tier 實例可達 10,000–50,000+ QPS，每輪對話約 2–3 次 Redis 操作。

換算下來約每秒 3,000–15,000 個活躍對話輪；一個 session 序列化後 2–5KB，5GB 可放超過 100 萬台購物車。

原文的結論是這層永遠不會是瓶頸——它同時快過上游 webhook 與下游 LLM 推理。

平台本身無狀態，每則簡訊都是孤立事件。原文的旅程是早上 9 點傳「加一加侖牛奶」，然後關掉去搭車。

下午 2 點再傳「再加麵包和蛋，多少錢」，系統得瞬間接回同一台購物車並重算總額。

付款只放 token 化的 payment_ref，模型只看得到「Visa ending in 4242」，卡號不進 prompt。

多代理最常見的質疑是 token 帳單：每一步都重送整段歷史，很容易吃掉零售毛利。

原文的判準很一致：能寫成程式碼的步驟，就不該留給模型推理。

原文三招都不靠模型折扣——狀態推出模型外、重活交給程式碼、路由與推理分層。

代價原文自己講了，叫「蜂群稅」：跨多次 LLM 呼叫的推理要 2–4 秒，所以 worker 先送一句進度提示，再串流結果。

進度提示補的是體感，不是延遲——那 2–4 秒並沒有被架構消掉。

限定語別漏掉：這是原型。5／5 自動化測試通過（0.158 秒）只證明流程跑得通，樣本是個位數次數的單筆實測。
