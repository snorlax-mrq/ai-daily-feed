1 個檔案專案唯一必需檔 agent.py，其餘能力都是可加選的資料夾
2 個函式create_deep_agent 回傳已編譯代理，define_deep_agent 只回傳定義

把代理寫成一個資料夾：你只交 instructions 與 tools，LangSmith 替你跑 harness、thread、沙箱與排程。

四格裡只有第一格是你寫的檔案；後面的部署、執行與對外服務，原本都是團隊自己接的線。

支援型代理是最小可懂的樣本：在 Slack 頻道答問題、每晚掃一次過期工單，兩件事各寫成一個檔案。

那份清單有夠長：重啟後還活著的 thread、能安全跑程式碼的地方、跨對話的記憶、做過什麼的紀錄，再加一台 cron。

原文的動機很直白：代理不進正式環境，就不可能主動，也不可能多人共用。

整篇是產品公告兼快速上手；原文只給最小可跑的骨架程式碼（agent.py、CLI、schedule 各一段），其餘都在 quickstart。

更新註記也寫得很清楚：私有 beta 起於 2026-05-13，本文描述的是 2026-11-02 當天可用的做法。

專案裡常見的幾個路徑，各自對應一個已開好的能力（節錄五項；memory.py、channels/、sandbox/、identity.py、evals/ 見原文）

mda deploy 掃到什麼就設什麼，所以專案可以從單一個 agent.py 長起，再逐項加資料夾。

研究助理的定義只有三欄：名稱、model 指到 openai:gpt-5.5、tools 放 web_search。

（編輯推論：playbook 何時被載入由代理自己判斷，寫得太泛用就可能在不對的時機被拉進來。）

有些能力連檔案都不用：內建網頁搜尋由 Parallel 提供，不必另開帳號或 API 金鑰。

瀏覽器遇到要登入的站台會把控制權交回你；想在指定工具呼叫前停下來等人核准，就在定義裡設 interrupt_on。

三個 mda 指令走完上線（前置還有 uv sync）：mda init 建骨架、mda dev 起本機伺服器、mda deploy 送上雲。

mda dev 那台本機 Agent Server 開在 LangSmith Studio：可以直接對話、看 trace，滿意了再按 deploy。

Context Hub：指令與記憶共用一份，維運因此變成改字

指令與記憶放在同一處，好處是改字變成資料變更：直接改 Hub，不必等下一次部署。

記憶也住這裡。學會你們的升級通報路徑後，代理在之後每一次對話都留著它。

若上次部署後有人改過 Hub 的副本，CLI 會先問你保留哪一版，不會默默覆蓋。

原文以自家三個代理當樣本：GTM Agent、Open SWE 與 Content Studio 都跑在託管版上。

（編輯觀點：原文把 Engine「提修改建議」寫成現成能力，卻沒給命中率或採用率；這仍是待人工複核的建議，不是自動修好。）

帶走三件事

平台收走的是維運，不是智力。代理好壞仍看你寫的 instructions 與 tools。

換掉的是編譯權，不是 harness。要主機掌控權就留在開源 SDK，別期待能力變多。

八成的縮減是自家產品自報。拿它當搬遷的訊號，不要當成自己專案的預期。
