先探索再出題：把正確答案做成資料的性質

5,144 個任務從 9,749 條 DAG 軌跡反推、經五維審查後留下的可驗證任務
0% 落入 No Data訓練期間 Agent 的工具呼叫全被模擬器接住（Exact 42.2%／Fuzzy 57.8%）
28.1% → 41.5%Qwen3-4B 在 Firefly 測試集的 pass@1，同評估協議下對比 Claude Sonnet 4.6 的 42.2%
約 US$47K用 Claude Sonnet 4.5 生成整份資料集的一次性成本（約 23.5B tokens）

問題不在「怎麼出更好的題」，而在出題與觀察誰先發生。

工具呼叫 Agent 要能用 RL 訓練，需要數千個任務，每個都要有正確的中間 tool call 與可驗證答案。

但主流 agent benchmark 一次只給幾十到幾百題，湊不出這個量。

原文逐一說明三條補資料的路線各有所長，但都無法同時做到「可靠、規模化、可驗證」。

路線卡在哪原文舉的代價
人工標註可靠但難規模化單筆通常 200 至 2,000 美元；獨家授權再高 4 到 5 倍
純模擬環境LLM 演工具，行為偏離真實 API學到的是「怎麼跟模擬器互動」
前向合成先出題、後求解，答案沒人保證題目可能根本做不到，solver 的錯答案被當成正解

第四個麻煩是 Environment Drift：真實 API 依賴搜尋索引、天氣、金融資料、DNS 等外部狀態，今天和明天的回傳可能不同。

加上 server 會下線、RL 的大量重複呼叫會撞上 rate limit，就算有了可驗證任務，訓練也難以重現。

把順序反過來：先看到答案，再回頭出題

原文的域名例子講得最清楚：LLM 先真的去查 whois，看到 amazon.com 是 1994 年、netflix.com 是 1997 年。

然後它才回頭寫出「哪個先註冊、差幾年」這道題；依原文給的兩個年份，差距是 3 年（編輯推算）。

正確性因此不是靠事後過濾，而是資料生成方式本身帶來的性質；原文稱之為 Verified by Construction。

同一條思路要撐到近千個工具，靠的是 Tool Graph 把探索導向語義上接得起來的鄰域，而不是型別硬湊。

產出的任務再用 LLM Judge 過五關：可驗證、有唯一正解、答案人看得懂、真實性評分不低於 5/10（全資料集平均 7.8/10）、難度標註與軌跡複雜度相符。

這一關大約刷掉一半候選任務；也因為題目圍繞 DAG 的節點子集生成，其餘節點自然成了干擾項。

訓練不碰 live API：模擬器三層接球

第三層的設計有個前提：每個任務都是從一條已知軌跡反推的，所以通往答案的路徑一定在快取裡。

（編輯推論：這等於用「題目只能出自走過的路」換取「訓練永遠有資料」；代價是模型在訓練時遇不到真正的新情況。）

資料規模：9,275 個候選任務最後留下 5,144 個，200 題做固定測試集、4,944 題訓練。

難度分布偏中：easy 19.5%、medium 77.0%、hard 3.5%；正解軌跡平均 3.0 次 tool call（範圍 1 到 10），答案 schema 平均 4.6 個欄位。

其中 38.5% 的任務要跨多個 server 組合工具——這正是多數 benchmark 限制在單一供應商時看不到的場景。

訓練設定：GRPO 加 Dynamic Filtering，每個 prompt 取 8 條 rollout；8 條全對的 prompt 永久移出訓練集，全錯的留著。

共 300 步，16 張 GPU 跑 actor、另 16 張跑非同步 rollout，框架是 Slime。

公開 benchmark 全部上升（Tau2-Bench Telecom 幅度較小），原文認為這說明模型不是背下了快取軌跡。

也要看清邊界：只訓練與評估 4B 模型；pass@1 與 pass@16 差距不大，作者推測 4B 已接近難題能力上限。

資料生成端也有邊界：篩選時排除有狀態與需要使用者認證的 server，而真實世界裡重要的工具常屬這兩類。

Fuzzy Match 那一層靠 LLM 生成回應，作者自己承認還說不準它多忠實於真實 API 行為。

（編輯觀點：這份資料集的壽命取決於「難度分佈」而不是「題數」——題再多，都落在 medium 也只練到某一層。）

（編輯觀點：hard 只占 3.5%，對更強的模型恐怕太淺——這份資料集的價值會隨模型變大而下降，除非難度分佈一起改。）

帶走三件事

順序決定正確性。先觀察再出題，答案不必再靠人工複核。

環境也要一起快取。只存題目不存回應，訓練照樣無法重現。

篩掉有狀態的 server。換來可驗證，代價是漏掉真實世界一大塊。
