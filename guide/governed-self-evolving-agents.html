Project Chrysalis 是研究參考架構：自演化 SRE 代理跑在 Gemini 平台與 ADK 上，自己能長出緩解工具，但每個補丁都要過四道治理閘門。

靜態 playbook 撐不住，三支柱解 SRE 三難

企業雲平台要服務數百萬並發使用者，緊耦合微服務的級聯故障，靜態 runbook 與閾值告警都預料不到。

Black Friday 快閃特賣這類高速事件裡，SRE 只有幾秒鐘讀懂嘈雜的分散式遙測，否則每分鐘燒掉數百萬美元。

生成式 copilot 加速了寫碼與日誌摘要，AI agent 仍難以可靠地修復線上事故。原文的例子：對抗連線池耗盡的值班工程師，不需要排查建議，也不需要未驗證的 PR。

差別在演化機制。傳統 agent 上線即凍結：system prompt 固定、工具預先註冊。

自演化架構在執行期合成情境專屬的緩解工具、為每次介入評分遙測影響，並把驗證過的護欄編纂給下一次事故。

進化的依據只能是「什麼有效、什麼失敗」的實證。原文把自演化雲端代理定位為應用研究的活躍領域，不是已上線產品。

原文把難題叫 SRE 三難：探索安全、結構可變性、多步功勞分配。三支柱各解一環。

四道驗證邊界，一條不間斷的保管鏈

原文把治理寫成防禦縱深：安全、可靠、對齊、可控，每個自主動作都被 Google Cloud 安全棧以密碼學方式框限。

每個合成補丁、蒸餾記憶與拓撲更新，都必須依序通過四個驗證邊界，一條不間斷的 chain of custody。

治理對象不只程式碼：蒸餾出的記憶與拓撲更新一樣要過這四關。

Model Armor 擋的是事故期間滿天飛的日誌與告警，那正是夾帶惡意指令的高風險通道。

四關各擋一種失敗：入口的髒資料與危險語法、沒簽章的程式碼、越線的參數與沒人簽核的結構變更、事後說不清的稽核斷點（編輯推論）。

四道閘由平台側執行，不靠 agent 自律（編輯推論）。驗的是簽章與政策，不是 agent 的自我宣告。

「Dual-Custody」借金庫雙人保管的比喻是編輯補充（編輯推論）；原文只說，Tier-2 結構變更要 SRE 持 token 明確簽核。

鏈尾把每道判決寫成可稽核紀錄，才讓「放手讓 agent 動手」變成事後查得清的決策。
