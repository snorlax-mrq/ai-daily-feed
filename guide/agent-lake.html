代理資料湖：trace 多到看不完，除錯要換一層引擎

trace 是「代理做了什麼」的系統紀錄；當它變長又變多，逐條人工除錯就撐不住了。

trace 含使用者意圖、執行軌跡與最後結果。最簡單的用法是當除錯工具：把步驟畫出來，看哪一步壞了。

但代理變強、進了生產，trace 又長又多，逐條人工檢視不再可行。原文說要規模化地用 trace 驅動改善，需要兩件事：為 trace 最佳化的資料庫，以及設計來查詢與處理它的「智慧運算」。

第一件已有成品：SmithDB。第二件是近幾個月的重點，理由是 trace 本身就是非結構化的推理紀錄，分析它也需要智慧。

架構因此長得像資料湖：一份共享語料，加上許多跑在上面的引擎。差別是 Snowflake、Databricks 的儲存與運算，都不是為代理資料設計的。

湖裡裝什麼：trace，還有 outcome

維度原文例子形式／數量
怎麼對應單一 trace 的倒讚、整段對話的低分一對一
怎麼對應合併的 PR：一段 thread 可開多個，一個 PR 也可由多段貢獻多對多
怎麼產生使用者直接給、觀察代理互動的系統、LLM-as-a-judge 代理指標、人工在標註佇列標記四種來源

湖裡多數是 trace：從使用者輸入、每一次模型呼叫與工具呼叫，到最後輸出；多輪對話以 thread 分組，讓整段互動可一起讀。

規模是自述數字：LangSmith 每月匯入數十億次執行的 trace，客戶 Clay 每天送上數億筆事件。

湖裡還有 outcome。trace 說代理怎麼做，outcome 說這樣做有沒有用；原文認為判斷 ROI 靠的是後者。

第一件事：撈出值得看的那幾條

線上評測器是起點：LangSmith 內建一批調校過的提示，直接替 trace 打幻覺、毒性與滿意度分數。

原文提醒別照單全收——要確認這些評測抓到的是你關心的訊號，不對就調整。成本是另一道牆。

原文提到 TypeSafe AI 在 9 月推出 decision model，讓生產 trace 的分類變便宜；LangSmith 已提供數個，這條低成本路線仍在研究中。

評分留在 trace 上的好處是查詢容易：用 feedback 篩選就撈得到；代價是要先定義要量的訊號。

若想在當下就找、不想事先建評測器，就用 AI Search：自然語言加上語意濾網，可再疊結構化條件。

第二件事：把改善迴圈自動化

撈出高訊號只是迴圈的一段。之後還得有人判斷它們代表什麼、代理該改哪裡；在客戶的量級下，這段也得自動化，於是 LangChain 自己做代理來跑。

Insights 回答「人到底怎麼用你的代理」：問一句「我的代理在哪裡失敗」，它把近期 trace 分組，並持續把新對話歸類，看得出哪類需求正在惡化。

Engine 找可修的問題：定期掃 trace，把重複失敗聚成 issue；接上程式庫後查根因、開修補 PR，v2 起還能在團隊看到之前先拿評測集驗證修法。

若改了 harness 仍反覆犯同一個錯，下一步常是訓練專屬模型，而湖裡已有現成語料：SmithTune 用最佳軌跡微調，再回 LangSmith 與基線比較。

原文以 Engine 自己當例：用某個代理的軌跡微調 Kimi K3，在 IssueBench 子集上拿下 96 分，基線 Kimi K3 為 90、GPT-5.6 Sol 為 87。

原文的收尾很直白：價值不在單一條 trace，而在你能在湖上做的事。

（編輯觀點：這其實是把 LLM 可觀測性推進成資料工程問題——儲存、語料治理與查詢成本，才是規模化的瓶頸。）

原文沒公布 SmithDB 的查詢延遲、儲存成本與資料保留政策；6,000 萬條與各項分數皆為自述。

帶走三件事

trace 是新的企業資料。儲存與查詢都要為它重做。

找訊號要自動化。評測器事前定義，AI Search 事後追問。

別只存過程。沒有 outcome，說不出代理值不值。
