Claude 應用 AI（Applied AI）團隊觀察到一個企業部署模式：把 router、planner、領域子代理摺疊回單一主 agent 迴圈，改用 skills 的漸進式揭露與 tool search 按需載入脈絡與工具——在多家企業部署的比較中，配備 skills 的單一 agent 在品質上常勝過「一個提示詞包辦一切」與子代理設計，每任務成本與延遲往往還更低。官方同步釋出 migration kit：先在 mock 系統的 demo 上試跑，再以引導式流程辨識模式、評估替代方案、驗證最佳做法。

  • 子代理沒有過時：驗證、平行工作、模組化權限仍該用它——但要按 context 切分、交回精簡結果。
  • 摺疊是分階段工程：建 eval set → 邊走邊量 routing 準確率 → 摺疊後改量 skill／工具載入對不對。
  • 單一迴圈需要紀律：精心管理的 system prompt、時機剛好的 skill 描述、對 context 與記憶的刻意處理。

為什麼要摺疊：企業 agent 的典型失敗模式

企業想做一個統合多項產品與能力的單一客戶介面 agent，而每個能力通常歸個別團隊所有。最順手的起點，是讓每個團隊自建 agent、再由中央平台團隊在上面蓋一層 orchestrator——結構可能是 orchestrator-subagent，或是把各團隊的 agent 以 MCP 工具暴露給單一 agent。這看起來最直觀，卻立刻引入新的複雜度。原文點名一個一再出現的架構路徑：意圖分類器 → 固定多步推理管線 → 使用者分群 → 獨立推薦分支 → 頂層多代理 orchestrator。

而回饋往往是：這些結構大部分在做「模型已經不需要別人代勞的工作」——一個清楚的 system prompt、4-5 個薄資料工具、加上嚴格的輸出護欄，就能涵蓋大部分使用情境。實例：某企業的客戶端 agent 養了一打專家子代理，結果一致的品牌體驗難以維持，多層轉發的延遲直接拖垮使用者體驗。這種現象有個名字：把架構做成組織圖的複製品——Conway 定律在 agent 架構上的作用。作為對照，原文的核心比較結論是：在多家企業部署的評比裡，配備 skills 的單一 agent 在品質上頻繁勝過「一提示通吃」與子代理設計，且常以更低的每任務成本與延遲達成。

替代設計：一個迴圈＋漸進式揭露

要協調跨團隊的專家，orchestrator-subagent 仍是合理做法；但原文主張一條往往更有效的路：漸進式揭露（progressive disclosure）——用 skills 漸進揭露脈絡、用 tool search 漸進揭露工具。agent 平時只看見 skills 與工具的短描述，需要時才完整載入。單一迴圈的好處之一，是讓 agent 學到的一切留在同一個 context，正好呼應許多團隊的終局目標：一個理解使用者高層目標、能代其行動的 agent。

代價是紀律：精心管理的 system prompt、時機剛好的 skill 與工具描述觸發，以及對 context window、記憶與筆記的刻意處理。組織層面，原文建議由一個中央團隊掌握端到端品質與 system prompt，每個新工具與 eval 上線前都要審核；中央團隊保持小規模，迭代才快、跨部門協調成本才低。

子代理仍有一席之地，包括研究前沿。原文定義：子代理是擁有自己 context window、工具與指令、由 coordinator 編排的 agent，強項是驗證、平行工作、模組化權限——Anthropic 自家的多代理研究系統也在用。問題不在「要不要用」，而在「為什麼用」。

真要多代理時：按 context 切，不按部門切

若確定走多代理路線，原文的原則是從最簡單、可能就夠用的模式起步（generator-verifier、orchestrator-subagent 等）。劃邊界時要按 context 切分：給每個子代理一段幾乎不需要系統其他部分支援的工作，做完交回精簡的結果。原文點名的適合候選：獨立的研究路徑、介面乾淨的獨立元件、黑箱驗證。

反例是按問題類型切分：子代理之間來回傳話，淪為「傳聲遊戲」（telephone game）——每多一次交接，資訊保真度就再折損一次。這正是「為每個團隊或問題類型各設一個子代理」的組織慣性，最終反噬品質的原因。

怎麼搬：分階段的遷移與量測

01先建量尺

一套共享的端到端 eval set，10 筆黃金範例就能起步

判斷該不該摺疊，先要有能比較的量尺。原文見效的結構：中央團隊擁有一套共享的端到端 eval set，各 skill 由擁有團隊隨附自己的小型 eval set。即使只有 10 個黃金範例，也足以開始。

02量對的東西

orchestrator 還在時量路由，摺疊後改量 skill 與工具

起步做法：用評分準則（rubric）給 agent 的最終回覆評分，追蹤回答品質。仍有 orchestrator 時，加測路由準確率（有沒有選對子代理）；子代理摺入後，改查 agent 是否載入正確的 skill、呼叫正確的工具。

03走向任務完成

長期目標是 task-completion eval

逐步把評測推向任務完成率——在比較不同架構時，這才是最有分量的指標。內部系統難以重放、使用者互動難以模擬的環境，量測本身就是工程題；原文分享的內部做法之一，是記錄時間戳。

04工具相助

migration kit：先在 mock 系統上試跑

配套的 migration kit 走引導式工作流程：辨識你的架構模式、評估替代方案、驗證最佳做法；內附 demo，可先在 mock 系統上演練，確認無虞後再套到真實 agent。

帶走三件事

模型變強，架構要跟著變薄。原文最鋒利的一句回饋是「大部分結構在做模型已不需要被代勞的事」——昨天必要的分類器與多步管線，今天可能只剩延遲與維護成本。

別讓組織圖變成架構圖。每個團隊一個子代理是最順手的起點，卻養出傳聲遊戲與難以一致的品牌體驗；按 context 劃邊界、交回精簡結果，才是多代理的切分原則。

架構之爭，先變成 eval 之爭。10 筆黃金範例＋rubric 就能起步：先量路由、摺疊後量 skill 載入、終點是任務完成率——沒有共同量尺，「摺不摺疊」只是品味問題。
