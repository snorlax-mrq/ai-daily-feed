30 秒版本

Thorsten Ball（據其 X 簡介，Amp 團隊工程師）把私訊朋友的 agent 心得整理成 15 條守則，幾乎每條都反直覺：模型用最新的別省、slop 別怕、Prompt 說 What 不說 How、不要跟 agent 來回迭代（叫它自己生出 20 個變體讓你挑）、context 別手動管、code review 只看爆炸半徑大的檔案。底層邏輯一致：讓 agent 看見並觸及整條 SDLC，幻覺自然消失；信任靠不可反駁的證據，不靠感覺。

  • 工具呼叫治好了幻覺：agent 看不見的就會編造——讓它跑 build、看日誌、部署、盯 rollout、回信給客戶。
  • 「要不可反駁的證明」是他口中最大的遊戲規則改變者：端到端走查、demo 影片、前後對照數字。
  • 節奏反轉：lean into async——派更大的任務、批次交付、用心跳排程，讓 agent 等你，不是你等 agent。

模型、slop、與 Prompt 的說法

第一條就燒錢：用最新最強的模型，其他都是浪費時間。他的算術是修辭式的（原文數字為例示，非量測）：模型錯 10% 的時候，你不知道錯的是哪 10%，只能反覆重試；省 50% 聘個「隨機笨 20%」的通才，代價算不過來。「Who's still using Opus 4.5? Exactly.」——這句同時暴露了文章的時效性：這是他「截至 2026 年 10 月」的配置。

第二條拆掉最常見的反對理由：別怕累積 slop。AI 生成碼會把 codebase 變成不可維護的泥沼？「半年前也許是，現在我不再確定——就算會，我也不相信結果是不可維護的。」第三條是 prompting 心法：描述 What，不描述 How。「把 bytecode 編譯器和 VM 做到極限快，不達 2 倍不准停」＋「最終應該長這樣」——目標與驗收說清楚，實作路徑讓 agent 自己找。

省模型錢＝反覆重試slop 恐懼過時了說 How 綁死解法空間時效：2026-10 配置

讓整條 SDLC 對 agent 可見

這篇的技術核心其實只有一句：是工具呼叫治好了幻覺。什麼讓幻覺消失？Tool calls——它們讓 agent 觸及我們的真實世界。如果 agent 看不見某個東西，它就會編造。所以解法是把整條 SDLC 打開給它看：跑起它建的東西（end to end）、讀 production 日誌、部署、盯 rollout、切 release、開關 feature flag、triage bug report、寄信給客戶——凡是你可以看的，agent 就應該可以看。

配套動作有兩個：給它 SDLC 的工具（他們做了 bug 回報、寄信給用戶、「系統健康嗎？」、開關 feature flag 的客製插件）；以及評估 agent 知識——AGENTS.md、skills、腳本、文件在 codebase 裡堆積，但 agent 真的會用嗎？派五個「盲測」agent，控制組對實驗組，跑實驗就知道。「Agents are really, really good at running experiments.」剩下的一條是坦白：local dev 現在很彆扭——遠端機器上 agent 各自裝環境很容易，本機則容易踩資源衝突。

換掉工作節奏：證據、非同步、心跳

第四組守則改變的是「人怎麼配合 agent」。不要跟 agent 來回迭代——別「試試看……啊不對，換那個」，而是「生成 20 個變體加一個小頁面，讓我組合測試」；這招連問題空間都適用：「給我 4 個『為什麼這麼慢』的理論，然後四個都查掉」。

要不可反駁的證明——他稱之為最大的遊戲規則改變者。agent 非常擅長產出證據：端到端走查、demo 影片、前後對照數字。你必須練出對這種證據的信任手感，還要在 AGENTS.md 裡寫上 「this is not evidence」，劃清什麼不算數。

節奏本身也要反轉：讓 agent 等你，不是你等 agent。擔心 TTFT（首 token 時間）大概是用法錯了；lean into async——派更大的任務、更野心，批次而不是來回。排程與心跳是殺手級功能：「兩小時後查 log」「上線了跟我說」「每天早上九點檢查一次」——他沒意識到多需要這個，直到不能再用。

記憶與審查：threads 是公司記憶，只看爆炸半徑

context 管理的答案很灑脫：別手動管。每個花在「現在是 30 萬還是 38 萬 token」上的念頭都是浪費——compaction 好用到不可思議。紀律只有一條：一條 thread 一個任務；他的 thread 有些 46 則訊息，有些 3,714 則。更進一步（以 Amp 為例），threads 是公司的記憶：「當初為什麼這樣做？」的答案就躺在 thread 裡，而且 thread 連著 git commit——避免重複工。

收尾兩條是減法。別讓 agent 寫給人看的東西——例外是除錯步驟、事件報告、部分文件這類「機械性」內容。code review 只看爆炸半徑大的：核心檔案不到 5 個，他逐一審；DB migration 要審；closure 寫法、型別優雅度、變數名、甚至重複碼——「I don't care anymore.」他的審查清單只剩四問：能用嗎？我懂到「圖上箭頭」的層級了嗎？agent 端到端測過了嗎？一個月後我還改得動嗎？

帶走三件事

能見度是幻覺的解藥。「看不見的就會編造」不是比喻而是機制：幻覺下降的歷史拐點就是 tool calls。與其調 prompt 求 Agent 別幻覺，不如把 build、日誌、部署、rollout 一路打開給它。

信任要靠機制，不靠感覺。「不可反駁的證明」建立門檻，爆炸半徑決定審查範圍——人的注意力是稀缺資源，只花在炸了會沉船的地方。

人的角色升級成出題者與驗收者。說 What 不說 How、批次派大任務、用心跳排程、讓 agent 等你——把「等待」和「來回微調」從工作流裡刪掉，是這 15 條守則共同的底色。

五個關鍵詞

SDLC 可見性讓 agent 看得見軟體開發全流程：build、日誌、部署、rollout、客戶回饋。看得見的才不會被編造——幻覺的結構性解法。
不可反駁的證明端到端走查、demo 影片、前後數字——可驗證的完成證據。把「agent 說做完了」變成「可以自己驗證做完了」。
心跳排程排程任務＋喚醒：定時查 log、上線通知、每日檢查。從「人盯 agent」變成「agent 定時回報」。
爆炸半徑一段程式碼出錯時的波及範圍。review 只花在半徑大的：核心檔案與 DB migration。
一 thread 一任務context 紀律：任務與 thread 一一對應，長度交給 compaction。thread 順帶長成公司記憶——連著 git commit。
