這是一篇個人經驗談，不是研究：15 條守則底下只有一個動作——先把任務說清楚，再要求可驗證的證據，審查只留爆炸半徑大的地方。

開路在前：先讓 agent 看得見，才談它做得好不好

他的順序不是「寫 prompt → 等結果 → 改 prompt」。動手前兩步就定調：挑模型，把目標與終態寫清楚。

第三步最反直覺：把整條 SDLC 打開給 agent。清單很長——讓它跑自己建的東西、讀 production 日誌、部署、盯 rollout、切 release、開 flag、triage bug report、寄信給客戶。

理由講的是機制不是激勵：「If the agent can't see something, it makes it up.」看不見的就會被編造。

所以他要求「eval agent 的知識」：AGENTS.md、skills、腳本在 repo 裡堆積，但 agent 真的會用嗎？派五個盲測 agent，對照組與實驗組跑過就知道。

原文還有一條坦白：本機開發現在很彆扭。agent 要自己裝環境、跑到端到端，遠端機器容易，本機容易撞資源。

thread 也是他的記憶體：原文說團隊越常用，越容易回答「當初為什麼這樣做」——因為 thread 連著 git commit，可以避免重複工。

五個原則，沒有一個是關於 prompt 措辭

節奏那組最不像工程建議：「別等你的 agent，讓它等你」。原文說還在擔心 TTFT 大概是用錯了，改派更大的任務、更野心、批次交付。

排程與心跳是他自稱的殺手級功能，而且是被關掉才發現：「兩小時後查 log」「上線了跟我說」「每天早上九點檢查一次」。

兩條減法也值得抄：別讓 agent 寫給人看的東西（除錯步驟、事件報告這類機械性內容例外）；context 別手動管，每個「現在是 30 萬還是 38 萬 token」的念頭都是浪費。

哪幾條站得住：主張按強度分三級

先把三類分開：① 他環境裡可查的事（核心檔不到 5 個、thread 46 與 3,714 則並存）；② 個人偏好（模型只用最新最強）；③ 通則化主張（slop 不要怕、工具呼叫治好了幻覺）。

① 幾乎不用爭，也最好抄：8 個 SDLC 動作（本站圖解 A 併為 5 類）、五個盲測 agent、bug 回報與 flag 外掛，都是他實際在做的事。

主張類型依據強度編輯觀點
工具呼叫治好了幻覺③ 主張中：機制說得通（看不見就編造），但原文只給因果敘述，無量測（編輯觀點：能見度解的是「看不到」，不是「看錯」；工具回錯時它會理直氣壯）

核心檔案不到 5 個① 事實高：可對照自家 repo 檔數與改動頻率這是他審查策略的前提，不是通則

→ 可橫向滑動

最該打折的是「別怕 slop」：原文自己寫「六個月前也許是」，接著給的是「我不再確定」——體感，不是量測。

模型那條同理：「Who's still using Opus 4.5?」把整條建議綁在 2026 年 10 月的配置上，過了這個時間點就要重算。

（編輯觀點：這 15 條幾乎都在描述「一個人＋一台機器」。團隊協作只佔一條——threads 是公司記憶，那是全文最薄、也最值得追問的地方。）

讀它的方式建議是：把 ③ 當假設，自己跑一次對照——原文示範過怎麼派 agent 做實驗，這招比照抄結論划算。

閱讀前提。這是個人經驗談，非研究或官方文件。作者為 Amp 團隊工程師（據其 X 簡介），threads 功能以 Amp 為例。文中數字多為修辭用例（10%、便宜 50%、笨 20%），全篇未附量測。原文口語、有多處筆誤（featuer、inicident、ambitous），本導讀按文意轉寫。

帶走三件事

先開路，再交任務。能見度是幻覺的解藥，不是更會寫 prompt。

驗收要能自己驗。證據加爆炸半徑，注意力才花得省。

原文有時效，也有立場。15 條是 2026-10 的個人配置，不是定律。
