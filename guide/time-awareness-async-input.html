代理的時間感：等到回覆是加分，準時交件是底線

個人代理缺的不是更快的模型，而是知道現在幾點、還剩多少時間、以及問不到答案時怎麼收尾。

原文的起點是一場 15 分鐘後的會議：先留 3 分鐘閱讀，代理實際只有 12 分鐘準備簡報。

它會發現使用者沒說這場是技術評估還是報價討論，而這個差別決定要查什麼、簡報該寫什麼，於是決定先問。

期限也是提示詞的一部分：會議時間與交件時間都寫進使用者訊息，代理才有依據判斷還剩多少餘裕。

期限愈近，原文說模型可以優先檢查最強的發現並開始寫，而不是再開一條研究線；期限給得寬，它就知道可以查得更深。

時間感不是塞一個時鐘給模型就結束：應用程式要把「再 15 分鐘」換成絕對時間戳，模型與程式才共用同一份時間資料。

四個環節，與最容易漏的接收端

要跑起這條流程，原文只動三個地方：開時間感、把內建搜尋設為即時模式、把提問做成非同步工具；第四個環節是回傳結果。

真正會漏的是提問的接收端：非同步問題不會出現在 required_actions，那份清單只描述阻塞動作。

環節原文設定／事件限定語與陷阱
時間感experimental.time_awareness 設 true模型會定期收到當前時間提醒，可據此調整工作節奏
提問工具function tool request_user_input_async，async 設 true代理繼續工作，應用程式同時等使用者回覆
事件入口agent.session.turn.item.done 裡的 function_call問題與選項在 item.arguments；等 required_actions 會漏掉非同步問題
回傳結果answered 帶 answer，或 no_answer截止時同一個 call_id 仍待答，就回 no_answer；一個待答呼叫只回一次

提問工具還能帶 choices：介面可把回覆做成建議選項，替使用者省下打字的時間。

示範中的應用程式在 4:10 關閉未答問題，比交件早兩分鐘；代理若提早跑完，介面上也要把待答問題關掉。

兩條路：平台送時間，或自己送

同樣的行為，原文給了兩條實作路徑。用 Agents API，時間提醒由平台送；自己寫 Responses API 迴圈，就得自己送。

手寫迴圈同樣在 tools 定義裡替提問工具標上 async，非同步行為才成立。

手寫迴圈有兩個約定：請求保持序列，讓每一輪接續最新狀態；工具結果屬於前一輪的問題時，仍用最新完成的 response id 當 previous_response_id。

計時器要罩住整個迴圈，連請求與串流都算在內；期限先到，就交最新完整版，或明說沒有已驗證的發現。

交付才是驗收點

交付不是等 turn 自己結束：完成就送，並且至少留 3 分鐘給使用者讀。取回時找 role 為 assistant、phase 為 final_answer 的已完成訊息。

串流提早斷掉不必重跑，列出 session 的 turns 就能確認已存的狀態，再取回完成的內容。

原文也把責任劃清楚：收集使用者回覆是應用程式的責任，代理只負責拿到結果後繼續推進。

清理也在流程裡：手寫迴圈交付後要刪掉已儲存的 response；Agents API 版本收尾時取消進行中的 session，再刪掉 session 與 agent。

原文最後把這個模式定位成產品級慣例：ChatGPT 與其他 agent harness 也用同一套做法，在問清楚之前繼續做事。

（編輯觀點：時間感解掉的是節奏，不是正確性。期限一到照樣交件，等於把取捨壓力交回提示詞與產品設計。）

帶走三件事

時間感是輸入，不是自律。模型不會自己看錶，得靠平台或呼叫端餵時間。

非同步提問要自己接。事件流裡的 function_call 才是入口。

問不到也要能交件。截止回 no_answer，代理才會收斂成一份可用簡報。
