薄層編排器：中央只排順序，可靠性交給程式碼

薄編排器＝把狀態與控制流程放在模型之外：中央只排順序、只做可靠性檢查，其餘判斷全交給專家代理。

問題：一顆大腦知道太多

場景是 Meta 推薦系統的資料欄位 onboarding，管線是 config-as-code：Python 設定驅動 C++ 程式碼生成，再餵給資料處理服務與分析系統。

一個欄位要跨 3 個程式碼庫、3 種語言、最多 6 個管線階段，而且各階段必須同步。

原文觀察：厚編排器不會一開始就壞，它是在規模、多步驟、異質子系統同時上場時才失效——正好是你最需要它的時候。

第一版和大多數團隊一樣：養一個全能代理，塞進設定 schema、程式碼生成規則、管線路由、驗證要求，外加 10+ 個資料源的 population 慣例。

Demo 很漂亮，上線開始幻覺。知識過了某個 context 門檻後，多給反而變差：它把 A 子系統的欄位命名慣例套到 B，或用甲資料源的生成模式去灌乙——原文稱「概念交叉污染」。

折衷版也量過：每個任務由工程師手工打造 system prompt 可到 70–80%，拿掉這層呵護掉到 10–20%。原文的結論：這不是 prompt 問題，是架構問題。

全頁成效數字（1,300 行、20+ 工作流、<1 小時、約 2/3 變更免人工）皆為 Meta 自報，無第三方驗證。Mount Sinai 數據出自 Windreich 人工智慧與人類健康學系預印本，未經同儕審查。

同一份預印本另報：多代理的 token 用量最多省 65 倍，作者歸因於任務隔離、避免 context 干擾。

預印本把機制講白了：多代理贏在任務隔離，贏在沒有共用的 context。

協定：7 步裡只有 1 步是 LLM

編排器的職責只有兩項：順序、可靠性檢查。它自己也「零領域工作」。

工作流模板是確定性狀態機，把「哪些階段、什麼順序」寫死，只留階段內的專業判斷給 LLM。

委派時 context 已由模板備妥，subagent 不必自己翻找，只在自己那份知識裡判斷。

幻覺因此不容易發生；真的發生了，也只壞在自己艙位，不會沿管線擴散成「派錯代理、抓錯欄位、跳過檢查」。

14 個 subagent 共用同一套標準結構——第 15 個長得跟第 1 個一樣，新增代理是套模板，不是綠地工程。

擴展：新用例寫模板，不寫代理

要支援 pipeline migration 這個全新用例時，團隊沒寫任何新代理，只寫了一份新模板，把既有代理換個順序排。

知識檔按工作流領域組織，執行時才載入；改檔案後下一個 session 自動用新版，同一份還能服務多個平台實作。

新欄位的設定準備：人工 3–4 天、早期設定驅動系統約 1 天、薄編排器壓到一小時內。

同前，成效為 Meta 自報。

可靠性檢查留在中央：路由、欄位蒐集、閘門都在確定性程式碼裡，模型沒有機會亂指路。

取捨寫得很直白：編排器是通用的，subagent 是專家。通用性換深度知識，是刻意的架構選擇。

下一步是把架構擴到新管線領域的更多資料欄位；compositional thesis 的預測是：規模化＝加模板與知識檔，不是重建代理。

也想要系統從生產使用中持續改進：自動回饋迴圈找失敗模式、提出對 subagent 知識的針對性修改，但任何變更仍由人審核把關。

帶走三件事

可靠性是架構問題。單代理拿掉手工 prompt 只剩 10–20%。

讓 LLM 只做只有 LLM 會做的事。順序與檢查寫成程式碼。

擴展靠組合。新用例＝新模板，知識更新＝改檔案。
