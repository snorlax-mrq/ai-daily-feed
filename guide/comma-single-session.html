常駐代理的護欄：一條會話、一份事實清單、一組證明

要讓 Agent 常駐，先解決「它自己會不會記錯、跑偏、讀到不該讀的」。

Comma 的架構是單一會話制：所有入口的訊息收進同一條主會話，由 Router 統籌，具體任務派給 Worker 平行執行。

Worker 有獨立上下文，做完把結果與來源交回 Router；使用者面對的是一條連續記錄。

上下文滿了會把較早內容壓縮出模型上下文，但原始紀錄完整保留——Router 可以回頭搜尋被壓縮掉的訊息與工具結果。

（編輯觀點：這等於把「記得」拆成兩件事：進得了模型的摘要，與留在磁碟上的證據。前者的品質決定它當下會不會蠢。）

事實清單是「精簡工作區」裡的一句一條：只放其他 Agent 也該知道的當前事實，例如一個決定、一位負責人、一項限制。

原文提到問法經過對比測試：用反向問法時，合適的事實也會拿到高機率，幾乎所有更新都被拒；改正向提問才拉得開。

訂機票的例子串起整套設計：先記下「靠窗、優先上午」，之後使用者說腰不好要改走道，過時檢查會提醒 Agent 更新舊條目。

三種判斷，三種後果

時機問 Jev 什麼觸發後會怎樣
寫入事實清單前這條內容是不是其他 Agent 也需要的當前事實？退回 Agent，由它決定是否確認後再送
每輪回覆後對話裡有沒有清單該補、或已經過時的事實？超過門檻就提醒 Agent 修改清單，是否採納由 Agent 判斷
每輪回覆後最近的回覆與工具呼叫，是否與清單或使用者要求相矛盾？提醒它先對照事實與請求重檢計畫

三個門檻都不是拍腦袋定的，而是用人工標註的樣本調出來的（原文未給具體數值）。

（編輯推論：把「要不要記」交給一個小模型擋，換來的是主模型的上下文乾淨；代價是多一次推論與一套標註工作。）

團隊版：記憶按受眾切，發送前先查權限

Comma for Teams 讓一個 Router 服務整個團隊，同時收群聊、私聊與私密頻道——但這些訊息的讀者不一樣。

做法是資訊流控制（IFC）：每份資訊標明誰有權讀，Agent 每次對外發送都要聲明用到哪些來源。

系統檢查目標對話的讀者是否都能讀這些來源；被攔下時 Agent 會收到原因，可去掉受限內容重發或請人批准。

判定由一個以 Lean 實作的檢查核心執行；長期記憶也照同一規則，寫成按受眾劃分的筆記，存在檔案裡讓使用者自己改。

另一條線是「等待」：需要盯著合約簽回、程式庫變更、機票價格時，Agent 會為每項監控寫一段 C 程式，編成 eBPF 常駐。

這些程式叫 Loop：等定時器或事件、檢查條件、必要時喚醒 Agent；需要語意判斷時就問 Jev，但實際操作與權限仍在 Agent 手上。

成千上萬個 Loop 跑在同一個行程裡，前提是每個只能碰自己的記憶體——執行時 async-ebpf 用約 4 萬行 Lean 證明確立這件事。

證明針對的是實際執行的程式：Rust 模組經 Charon 與 Aeneas 翻成 Lean 再證，連編 Loop 用的 C 編譯器也被編成 eBPF 丟進同一個沙箱。

（編輯觀點：這是全篇最不像「AI 產品」的一段——它把 Agent 自寫程式的風險，交給形式化證明而不是提示詞約束。）

最後是調度：每個任務歸類（比價訂票、整理郵件），調度層記錄每類用過的模型、推理強度、完成次數與花費。

成功以人工驗收為準，再選「每完成一個任務平均花費最低」的組合，並留少量任務試其他模型累積依據。

帶走三件事

記憶要能被檢查。一句一條、逐條問，比一整段摘要可靠。

會話收斂，權限不能收斂。單一會話下，記憶必須按受眾切。

Agent 寫程式要有硬邊界。沙箱靠證明，不靠它自己乖。
