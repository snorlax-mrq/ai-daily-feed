治理代理的稽核證據不是另寫一套文件，而是工程師平常除錯就在看的 trace、評測與權限設定。

原文先把問題講清楚：企業已把客戶資料、甚至營運系統交給代理，而代理是非確定性的——每次執行可能走不同路徑，途中還會改動其他系統。

治理難，所以需要共同標準。ISO/IEC 42001 規範企業怎麼治理 AI 系統、系統內建哪些控制；認證先做內部稽核，再由外部稽核員確認系統照文件運作。

對每個納入範圍的 AI 系統，稽核最後收斂成四問，原文也照這四問分節回答。

四問，先從權限邊界看起

第一問是權限邊界。演示方式很具體：請代理用一個需要核准的工具對 Slack 發文，執行因此暫停，他們附理由駁回，代理回報駁回且沒有重試。

這一幕能當證據，是因為 trace 記下整個過程——審批要求與它真的被執行，都在同一份紀錄裡。

變更控制走同一條路：系統提示在 Fleet 打開，就看得到誰可檢視、誰有權編輯。

不在程式庫管提示的團隊，則用 Prompt 與 Context Hub 的版本提交與可移動標籤，追蹤發布並還原舊版。

「可重現」指的是資料集與評測器

第二問是「怎麼證明它有效」。稽核員要兩樣東西：某個版本的測試結果，以及測試資料從哪來。

代理評測難重現——同樣輸入不保證同樣輸出。原文的說法是：能固定的是資料集與評測器，這樣分數變動才分得清是代理行為、還是測試本身變了。

他們的答案很硬：評測資料只來自自家跑的系統，不取自客戶工作區。

每個測試都記錄範例來源與評分程式碼，變更走 PR，留下帶日期的紀錄與審查者；於是版本歷史加上實驗，就構成那批測試結果的來歷。

他們也測評測本身：空白答案能過的測試直接丟棄、重複的 trace 移除；評分器先餵一題已知正確的答案，沒拿滿分就先查評分器。

有寫入權限的代理另要驗提示注入與資料外洩，LangSmith 內建涵蓋多數此類風險的預製評測器；需判斷的項目交給 LLM-as-judge，人工複核走標註佇列。

第三、四問：紀錄，然後回頭修

第三問要的是系統生命週期的活動紀錄與上線後監控。trace 能重建一次執行：輸入、輸出、工具呼叫、錯誤，連需要核准時的暫停與續跑都在同一份紀錄。

稽核員因此不必拼湊不同日誌；同一套評測也能跑在生產 trace 上，結果以回饋分數附在該次執行。

審查者點開被標記的回應，就看得到導致它的那些動作；人工修正也會存回 trace，成為後續評測的材料。

第四問要求系統持續改善。原文以 Engine 示範：它把重複失敗分組、進原始碼查根因、開出修補 PR，還能在 preview 環境先驗證，再走團隊原本的審查。

被修正的那次失誤，之後會變成評測資料集裡的範例——一次事故就換來一條回歸測試。

組織層面的政策、角色與風險評估同樣交給代理：Security Agent 以 Deep Agents 打造、跑在 LangSmith 上，自身執行被追蹤，工具也受同一套審批設定約束。

原文說這讓兩人的團隊撐起治理計畫，也支援 SOC 2、ISO 27001、GDPR、HIPAA 等多套規範的盤查。

（編輯觀點：這篇的價值不在證書，而在示範「合規證據＝既有觀測資料」——若為稽核另做一套，那才是真正的成本。）

原文沒給稽核工時、費用或缺失項數，也沒量化 Security Agent 省下多少人工。

帶走三件事

合規靠既有觀測。trace 與評測同時是除錯工具與稽核證據。

預設關閉才答得出來。四問問的是邊界，不是事後補救。

重現的是測試不是輸出。固定資料集與評測器，才說得清分數變化。
