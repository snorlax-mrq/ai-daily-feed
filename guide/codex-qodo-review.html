Codex 把局部任務做完，Qodo 補上跨庫脈絡與獨立審查；兩者來回，開發者開 PR 前就看到爭點。

原文要解的難題不是寫得快，是改得對：單看一處改動沒錯，卻可能弄壞下游服務。

Qodo 的本業是程式碼審查與軟體品質工具；它要給代理的，是「讀懂自己所改程式碼」所需的組織知識。

Qodo 在 Codex 市集上架外掛，透過自家 Agentic Toolbox，把三樣東西交給 Codex：程式碼知識、組織規則、獨立審查。

有了脈絡，Codex 才看得到跨 repo 的依賴，包含不同 Git 供應商託管的儲存庫，以及靠 Kafka 串接的服務。

原文那句：把軟體當整體看，才不會漏掉 P0 bug。

審查的時機也是設計的一部分。Codex 動手前先取回規則與 PR 歷史，改完後由 Qodo 審，發現直接回到同一個 session——此時開發者還沒開 PR。

模型標準很直白：要最前沿、最會推理，也要真的快。Qodo 用的是含 GPT-6 Astra 在內的 OpenAI 模型。

Friedman 的比喻是陰陽：一個生成程式碼，另一個挑戰它。兩個角色各要自己的設定與脈絡，也可能各有多個代理。

目標狀態是代理先互相討論，只把彼此不接受的部分上浮。人看到的不只是結論，還有討論、脈絡與過去的決策。

職稱也跟著改寫：開發者從寫手變成規劃者與審查者——這是願景，原文沒說已發生。

Qodo 的 AI 開發者關係負責人 Nnenna Ndukwe 說，開發者拿這套流程做新功能與技術債。

她說，GPT-6 模型在 Codex 裡寫、（編輯推論）交接自動化，Qodo 負責獨立審查（Qodo 自述）。

她自己也這樣用：以 GPT-6 Astra 的 Extra High 與 Ultra effort 排程 Codex，寫每週成果與下一步。

同一套流程也用來讀社群上關於 agentic engineering 的討論，檢視自己的變更，並建議該補哪些 agent skills。

200 條規則：先篩選，再推理

在他口中，規則數量本身就是瓶頸。他的例子是 200 條規則：API 先選出這一階段該檢查哪幾條，模型只推理相關的部分。

原文給的理由是更快、更便宜，審查品質也更好。這仍是構想——原文沒說 Qodo 已經上線這條路。

這條路也管 agent skills：每個階段該帶哪些技能，同樣可以交給 API 決定，不必讓模型每次重猜。

「軟體工廠」是他給的終點名稱：公司知識引導寫程式的代理，獨立審查檢查產出，剩下無解的問題交給人的專業。

Ndukwe 形容這套做法取的是「AI 的長處」加上「傳統軟體工程與腳本的長處」（原文為 Nnenna says）。

Friedman 則把它說成客戶可自行組裝、自己擁有的系統，並理解軟體在生產環境怎麼變。

（編輯觀點：把「選哪條規則」搬出模型，等於承認有些判斷該留給可稽核、可重跑的程式，而不是留在提示詞裡。）

帶走三件事

外掛賣的是脈絡，不是速度。跨 repo 依賴才是 P0 bug 的藏身處。

發現要回到同一個 session，不是開完 PR 再回補。晚一步，修的是人的時間。

只上浮未解爭點，前提是討論留下紀錄。沒有紀錄，人只收到結論。
