Agent 平台：四個人把原型時間砍掉兩個數量級

先把「每個團隊都要重做一次」的重活收成平台，agent 團隊只剩一件事要想：這個 agent 到底做什麼。

Workday 做 HR、財務與 IT 的雲端系統，客戶含過半 Fortune 500。它要在 2026 年底前把 agent 推上生產。

難處不是模型，是流程：任何內部服務要上線，都得先過稽核、法遵與資料保留政策。

選擇留下的自由度，與被收走的雜事

平台明確不替 agent 造型。原文對比的是把 agent 建模成「一連串對話」或「角色人設」的做法。

LangGraph 給的是圖：從最簡單的 ReAct 迴圈，到完全決定性的工作流，都同一套。

決定權留給寫 agent 的人，平台不預判 agent 該長什麼樣——這是原文反覆強調的設計取捨。

SDK 則把「Workday 版本」的每個 AI 概念重做一遍——閘道與檢索都在裡面。

工程師 Alex Gatto 的說法是：LangChain 每推出一個 AI 概念，他們就試著在 Workday 做一個同概念的 SDK。

平台有兩組使用者：內部寫 agent 的工程團隊，以及那些 agent 最終服務的客戶。

四人要扛的範圍原文列得很清楚：可長跑的 agent server、綁稽核政策的資料存取、協作式評測平台，以及把前三者包起來的 SDK。

這四件事任何一件單獨做都不難，難的是四個人同時做，還要能通過企業級的稽核。

時間壓力來自上面的目標：2025 年看到 agent 的市場機會，就訂下 2026 年底前要有 agent 進生產。

但 Workday 跑的是人資、財務與 IT 資料，任何一個 agent 碰到不該碰的欄位都是事故。

所以第一個產品不是 agent，而是治理層——先能回答「這個 agent 可以呼叫哪些 API」。

SDK 的存在理由也類似：所有呼叫都繞進內部 LLM 閘道與 RAG 服務，權限與稽核才收得攏。

「免費拿到」在組織裡的意思是：被問到時不用先做功課，協定策略的答案是既有事實。

結果是時間尺度的變化：原型 4 到 5 個月，而且不保證能上生產；現在不到一天就有 staging 環境。

而且那個 staging 環境已夾帶認證與安全需求，不是只會跑的 demo。

原文沒給「上生產」的數量，只說平台小組的人數與投入都在增加，這是最誠實的成效指標。

（編輯觀點：這篇真正賣的是「治理先行」的順序，而不是某個 agent 多聰明。）

節省下來的注意力去了哪裡？原文的答案很直白：只剩下「這個 agent 做什麼、圖長什麼樣」。

代價是平台小組得持續維護那層抽象並跟上遊改版；原文對擴編的解釋是與 LangChain 合作的成功。

如果把這篇當採購參考，重點是它示範了「先治理、再擴編」的順序，而不是某個框架比較好。

帶走三件事

平台化的收益是「注意力預算」。小組從 4 人長到約 30 人，替 agent 團隊省下的是注意力。

治理層要先上線，不是後補。先定義 agent 能碰哪些 API，再談擴編。

協定要選了才不會卡。A2A／MCP 內建，等於免掉一次架構重工。
