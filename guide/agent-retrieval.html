檢索管線外包：檔案丟進去，答案自帶頁碼

原文：Google Developers Blog 的實作教學，逐段示範建立 data store、匯入文件與影片，到用一次呼叫完成帶引用的搜尋（作者 Kaz Sato，Staff Developer Advocate）。

約 9 分鐘18 份 Alphabet 投資人 PDF 從公開 bucket 到可依頁碼搜尋（Google 自測）
0.3–0.5 秒19 分鐘影片每次查詢，含開啟音訊 embedding 的版本
5 種文件＋4 種影片格式：PDF／DOCX／PPTX／XLSX／TXT；MP4／MOV／WebM／MKV 等
2 個區域v1beta、走 REST；Public Preview 期間只開 us-east4 與 europe-west4

把檔案丟進 Cloud Storage，解析、切段與向量都交給服務；代理呼叫一次 API，就拿回帶頁碼或時間戳的段落。

匯入與查詢，各剩一次呼叫

原文開場先把成本講清楚：代理要回答 PDF 裡的問題，得先有人建管線——解析、切段、embed、寫進向量資料庫，最後還要學會它的 schema。

影片更貴：轉檔、切成片段、embed 畫格，還要記住每個片段來自哪支影片的第幾秒。

託管導入把前段變成設定：data store 指向 Cloud Storage，服務自己解析、切段，用 Gemini Embedding 2 產生向量。

文件與影片各用一種 document_type：文件是 UNSTRUCTURED，影片是 VIDEO，兩者分開建 data store。

查詢端只剩 data store 加一句文字查詢；Collection 名稱、向量欄位、task type、輸出欄位都不必傳。

文件查詢自動跑混合搜尋：語意與全文各查一次再融合，改寫過的問題與精確專有名詞都接得住。

回傳單位是段落不是檔案，同一個 PDF 可以回好幾筆，各帶自己的頁碼範圍。

六段線換了負責人

原文用一張對照表講差別；六列講的是責任轉移（編輯觀點），不是功能變強。

工作以前：自己接 Collection託管後：data store＋SearchDocuments
解析檔案自己處理 PDF、Office 檔與影片轉檔服務解析，格式清單見上方資料卡
切段自己決定邊界，自己記位置chunk 或 page，分頁文件（如 PDF）兩者都記頁碼
產生向量自己跑 embedding job 再寫入Gemini Embedding 2，寫進 backing Collection
懂 schema查詢前先弄清楚欄位怎麼存不必傳 Collection、向量欄位、輸出欄位
組查詢semantic 與 text 自己挑、自己併混合搜尋自動；reranking 一個開關
標出處自己回頭追原文第幾頁每筆結果自帶 URI 與頁碼或起訖秒

原文的結論也是這句：好的檢索需要什麼沒變，變的是誰來建。

以前要維護 parser、chunker、embedding job 與 schema；現在這些都不在你手上（編輯推論：代價是查詢端少了可微調的欄位）。

需要細控仍有退路：背後的 Collection 就是一般 Agent Retrieval Collection，可以直接查。

過濾走結果讀回的路徑（metadata、頁碼），也能只查指定 document_ids；原文示範用 page-1 過濾，把五份財報頭版的 CEO 談話一次撈出來。

排序同理：reranking 開啟後候選取多於 top_k，再用 Ranking API 重排。

原文實測很說明問題：問「Alphabet 有多少員工」，純混合搜尋前五名有兩頁是資產負債表；開 rerank 後每筆都在講人數，含年報的 190,234 人。

匯入是 long-running operation，失敗的檔案可以指定寫到某個 GCS 前綴，回頭再跑一次。

原文給的判準很直白：資料本來就是檔案，就交給 data store；只有需要它給不了的控制，才降到 Collection。

前提要一併讀：API 在 v1beta、走 REST，Python SDK 還在規劃。

服務帳號要拿到 roles/vectorsearch.serviceAgent，否則它讀不到你的 bucket。

影片的兩個旋鈕：窗長與音訊

影片 data store 只有兩個參數值得記：窗長與音訊。

預設 30 秒一窗；10–20 秒換精準時間戳，最長 80 秒換主題式查詢需要的上下文。

音訊預設關閉，只 embed 畫面，所以查「某人講了什麼」會落空。

原文的影片示範用場景描述查詢：「機器正在分揀小黃瓜」命中機器學習影片的 03:20–03:40，全片沒有標籤也沒有字幕。

影片的匯入成本比文件高（編輯觀點：這是最容易低估的一段）。

排程形狀也被規定：同一個 data store 一次跑一個匯入，不同 data store 之間才能平行。

成本分兩層看：Public Preview 期間託管導入不另收費，GA 起才計價。

介面目前只給 REST，原文明說 Python SDK 還在規劃；要細部控制時，仍可直接查背後的 Collection。

backing Collection 照 Agent Retrieval 標準價另計，這筆帳不會因為換了 API 就消失。

還有一個限制要記住：reranking_spec 不支援 VIDEO data store，排序微調只在文件端有。

刪 data store 要帶 force 與 backing_collection_deleted。

否則背後的 Collection 會留下來繼續計費；原文實測清除約 20 分鐘。

帶走三件事

瓶頸在匯入，不在查詢。影片匯入以分鐘計，查詢只花零點幾秒。

切段策略決定引用品質。chunk 與 page 換的是精度。

頁碼就是採用門檻。說不出出處的答案，沒人敢放進產品。
