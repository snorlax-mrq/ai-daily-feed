LLM 可靠性：改動的影響要能被量出來

2023 年 6 月下旬Dosu 上線；當時量體小到每個回覆都能人工看過，工具只有 grep 與 print
6 步原文給的 EDD 迴圈：少量 eval 起手 → 上線 → 生產找失敗 → 回填離線 eval → 迭代 → 重上線
4 類訊號找失敗模式用的線索：明確回饋、使用者情緒、內部錯誤、回應時間（原文並列，未排序）
數千個儲存庫Dosu 現況與「數十個子模組」皆為原文自述，無第三方驗證

EDD 把 eval 當成改動的對照基準：先量出代價，再談上線，失敗模式回填成下一輪的題目。

Dosu 是掛在 GitHub 上的 AI 隊友，替開源專案回答提問、分流 issue、標記 PR。作者 Devin Stein 是它的執行長。

起點是維護者的日常：專案越紅，回覆使用者吃掉的時間越多，有人索性宣告「issue 破產」——把未處理的 issue 與 PR 一次關掉。

原文引微軟 2019 年的研究：業界開發者最多 85% 的時間花在非寫程式的雜事上。Dosu 要接手的就是這一塊。

難處在改動不可預測。原文的描述是：微調一個提示詞，某個場景變好，另一個場景就退步。

所以 eval 不只是上線前的門檻，更是每次改動的對照基準。原文自己點明這層關係：EDD 與 TDD 一樣，先有終點再開發。

六步裡真正費力的是 03 與 04：失敗模式得從生產流量撈，再一則一則補成離線題目，題庫不是憑空寫的。

（編輯觀點：要求每個改動都回答「對使用者的影響」是作者的標準，不是產業共識；前提是每類改動都有對應的 eval。）

量體一大，第三步就斷了

2023 年 6 月剛上線時，量小到每個回覆都能看過。團隊每天用 grep 與 print 翻日誌，作者說痛苦，但因此摸清使用者怎麼用 Dosu。

現在 Dosu 裝在數千個儲存庫、有數十個子模組，全天候產出回覆（原文自述，無第三方驗證）。逐筆人眼檢視這條路走不通了。

而生產監控正好是 EDD 的 03。這一端斷掉，04 就沒有材料可回填，迴圈停在半途。

選型要求原文給的理由對 EDD 的作用（編輯整理）
提示詞進 Git把提示詞當程式碼，改動走與程式碼相同的標準版本對得上，才追得出是哪次改動造成退步
程式碼層級 trace一次 trace 內追蹤多次 LLM 請求之間的 metadata失敗常發生在請求之間，不在單次呼叫裡
資料可匯出既有的 eval 資料集與工具要留著用題庫不搬家，舊題目不必重寫
可自訂、可擴充LLM 應用沒有標準做法，要能決定追蹤哪些 metadata搜尋面能隨新失敗模式一起長

四項裡最關鍵的是第一項。提示詞不進版控，03 找到的失敗就無法釘在某一版上。

最後打動作者的是 SDK 而非介面。加一個 @traceable 裝飾器，原文稱幾分鐘完成埋點，上線後 trace 立刻湧入（Dosu 自報）。

這個裝飾器同時送出函式呼叫與 LLM 呼叫的紀錄，於是函式原始輸入、渲染後的提示詞、模型輸出都落在同一條 trace 裡。

失敗模式：四類訊號，沒有先後

失敗模式指 Dosu 處理不好的請求。輸入種類越多，失敗面越大，所以原文不靠猜，改看四類訊號。

四類訊號在 LangSmith 變成搜尋條件：明確回饋、近期錯誤事件、回應延遲、負面情緒；也能替 trace 掛自訂 metadata 擴大搜尋面。

抓到的第一個模式很具體：使用者貼上數千行日誌、或 OpenAI embedding 的原始浮點值時，回應會極慢。

另一則是團隊最愛講的：被要求替 PR 貼標籤，Dosu 回覆的卻是自己晚上要去的演唱會。

找到之後走的還是同一套：在 LangSmith 搜更多同類樣本 → 加進 eval 資料集 → 對著 eval 迭代 → 推新版 → 重複。

下一步是自動蒐集：從生產流量直接長出 eval 資料集，讓工程師按對話主題、使用者分群、請求類別自行整理。

原文收在一個飛輪：Dosu 變好，LangChain 團隊的維護負擔就減輕，於是有更多時間做 LangSmith，回頭又加速 Dosu。

（編輯觀點：全文沒有給任何量化改善，飛輪也只是作者的關係描述。讀者能確認流程存在，無法確認效果。）

帶走三件事

EDD 的瓶頸是題庫，不是工具。沒有把生產失敗回填成 eval，迴圈只是儀式。

規模一大，監控就是開發流程。03 一斷，04 到 06 全部空轉。

廠商客座的成效要打折看。數千個儲存庫、幾分鐘埋點都是自述，無第三方驗證。
