只為看到的那幾頁付費：Gemini API 把切片搬到伺服器端

原文：Google 在 Gemini API 推出檔案切片控制與原生 Office 檔案上傳，讓代理指定要看的頁面與片段

4 類媒體文件與簡報、試算表、影片、音訊都可指定範圍切片
14 倍Vercel 引述：抽單頁文字比整份 PDF 渲染少用的 token（原文引述，無獨立複核）
1 次上傳Files API 的 URI 可跨多輪與工具呼叫重複使用
所有 Gemini 4原生切片支援全系列；既有檔案大小與頁數上限不變

過去 API 只吃整份檔案，代理只好在客戶端自己切；現在切片、算繪與 token 化都搬到伺服器端，只為真正檢視的頁面計費。

知識工作藏在密集的 PDF、簡報、多分頁活頁簿與長錄音裡，整份丟進去多半是浪費。

原本的做法是在 harness 裡跑 LibreOffice、PDF 算繪器與 ffmpeg，先切好再上傳。

代價是記憶體膨脹、本機磁碟被抽出的影格塞滿，企業平台還得為每個使用者維護沙箱。

把檔案攤平成純文字也一樣有代價：版面、圖表與表格結構會先被丟掉。

新做法是把 Files API 的 URI 放進使用者回合或 function response，由 API 端依需要切片與算繪。

可控制的維度有四種：範圍、內容層、解析度與影格率，這也是「只為檢視部分計費」的計算基礎。

官方把它定位成「讓 harness 具備多模態，而不必在本地膨脹」：檔案不落地，抽取與算繪都在雲端。

對企業平台而言，這也把「每人一個沙箱」的成本，換成按 token 計費的 API 呼叫。

四類媒體，各有一套切片旋鈕

文件、試算表、影片、音訊的切片維度不同，可選的內容層也不一樣。

媒體可切範圍可選內容層

參數省略時有預設：文件與簡報走保留版面的頁面圖像；試算表預設帶入所有分頁的計算值、公式與工作表名稱。

四類媒體對應四種閱讀習慣：PDF 與簡報看頁、活頁簿看工作表與儲存格、影片與音訊看時間軸。

例如試算表可只取某個分頁的可見儲存格與公式，略過視覺層；對大型活頁簿特別省。

兩段式讀法：先掃描，再放大

官方示範的省法是把同一份 Word 檔上傳一次，先用抽取文字掃過全文，再回頭看單頁高解析圖像。

同一個 URI 可以跨回合重用，代理也能在 function response 的 function_result 裡直接指定要看哪一段，少一輪來回。

範例裡掃描用的是文字層，放大那一步才拉高解析度並只取 page_image，兩次呼叫各取所需。

對 agent harness 來說，檔案處理從「先下載、再轉檔、再切片」縮成一次 API 呼叫。

對多輪工作流來說，這等於把「先看目錄再翻頁」的習慣交給模型自己決定。

官方把這種省法叫「skim cheap, then zoom in」：先便宜掃過，再對真正重要的地方花高解析度 token。

（編輯觀點：真正省下的不只是 token，還有平台為切片而養的沙箱與算繪管線。）

兩家早期採用者怎麼算這筆帳

官方引用兩個合作夥伴的數字，兩者都是自家測試、未公開樣本與方法。

來源比較情境結果性質
Vercel抽單頁文字 vs 整份 PDF 算繪少 14 倍 token引述，未公開方法
LiteLLMPDF 切片prompt token 減 67%自家測試
LiteLLM活頁簿切片prompt token 減 33%自家測試

LiteLLM 的說法是：多數送 PDF、簡報與試算表的使用者，只需要幾頁或一張工作表。

它也表示這項功能可透過 LiteLLM 既有的 Gemini 路由使用，客戶端不必額外設定。

（編輯觀點：三組數字的基準不同，14 倍講的是整份算繪的浪費，67% 與 33% 講的是自家流量組成，不能相加比較。）

帶走三件事

省 token 只是表面。真正拆掉的是客戶端的算繪與沙箱。

切片要交給代理決定。它才知道下一輪該看哪一頁。

不指定就回預設。文件全頁算繪、試算表全分頁，費用照付。
