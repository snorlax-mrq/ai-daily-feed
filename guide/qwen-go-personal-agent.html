個人代理三件套：模型、記憶、生態

導讀

原文：機器之心〈對談千問蔣冠軍：從模型、記憶到生態，Personal Agent 的技術架構如何搭建？〉——人物訪談（受訪者為千問事業部 AI 演算法負責人）

機器之心·2026-11-05 發布·2026-11-08 收錄· 閱讀官方原文

30 多個行業千問拆解需求時劃分的行業範圍，對應 8,000 多項模型的原子能力要求
約 40%受訪者稱近一段時間千問相關任務的上下文規模降幅
70 元現金航班延誤理賠案例：Agent 拒收代金券、持續爭取後的實際結果
3 個核心模型、記憶、生態——受訪者說三者缺一都會影響交付

Personal Agent 的難點不是「更會聊天」，而是它得先知道你是誰、能動用什麼。

受訪者介紹的是千問正在邀測的 Personal Agent「千問 Go！」，並把技術框架收成三件事：模型、記憶、生態。

他對 Harness 的定義很具體：組織個人記憶、任務資訊、Skill 與工具，構成模型實際執行任務的環境。

因此模型與 Harness 不能分開看——模型看得到什麼上下文、能呼叫什麼工具，直接決定交付品質。

（編輯觀點：這段其實是在反對「換更強的模型就好」。他用的是成本論證：能用工具與 Skill 解決就少讓模型自己想。）

他也直說生態不通不是模型變強就能解決：能走 API、MCP 最好，其他方式還得看授權與服務方是否允許。

這條邊界，是通用 Personal Agent 繞不過去的部分。

記憶不是多存，是判斷「記什麼、怎麼用」

問題原文的例子受訪者的判準
記什麼使用者說「月薪 8,000 元」記數字，還是記「有穩定收入」的狀態
怎麼存退休養老＋孩子三十多歲沒工作兩件孤立事實連起來，可能是家庭焦慮的線索
何時召回同一位使用者問天氣問孩子就業可提養老金背景，問天氣不必提家庭

他把這套思路叫「需求驅動的記憶體系」：從「怎麼用」反推「該記什麼」，而不是盡量多存。

儲存形式反而次要——純文字仍然有效，因為模型的文字理解能力夠強；該投入的是內容選擇、粒度、分層與時效。

記憶還必須能更新、能失效，召回時要再判斷一次「這條還適用嗎」。

（編輯觀點：這與其說是資料庫設計，不如說是編輯判斷——難的是取捨標準，不是儲存引擎。）

穩定度靠原子能力，成本不只靠模型

他對「驚豔」與「長期使用」的區分很直白：前者看能力上限，後者看能力下限。

使用者的預期是「多數票都訂得成」，不會接受換一種票就失敗，所以千問繞著 30 多個行業，把需求拆成 8,000 多項「模型原子能力要求」。

作法是把不同表達聚類、歸約成可訓練的能力，再用後訓練與強化學習提升穩定性，最後組合起來覆蓋真實需求。

成本方面，他承認荒謬處境：幫使用者搶到 10 元優惠券，消耗的 token 成本可能更高。

解法分成三塊：模型路由與大小模型切換、推理優化，以及 Harness 本身——工具與 Skill 是平鋪還是分層、相似工具先選哪個，都會改變執行路徑與成本。

另一個動作是上下文壓縮：歷史對話提煉成記憶、短期 context 按任務篩選、工具資訊精簡；他稱近一段時間相關任務的上下文規模降低約 40%。

（編輯觀點：40% 是受訪者自述、沒有計算基準與基準日，只能當方向看。）

主動服務與操作邊界

航班延誤理賠的例子被用來解釋「目標不丟」：使用者要現金，Agent 就把代金券方案視為未完成，持續溝通並找到其他管道，最後獲賠 70 元現金。

但主動服務他講得很保守：目前還在初級探索，先挑需求與時間點明確的場景（例如健康復查節點），用產品設計限制範圍。

他的原則是「相關不等於應該反覆提起」：使用者提過不想多談的疾病，即使與後續健康問題相關，也不該每次都拿出來提醒。

長期目標也分難易：馬拉松成績可以和訓練、休息連起來；「我要升職」範圍太廣，目前還做不到可靠判斷。

操作邊界則是硬規則：涉及訂單、交易或個人資料修改，該由使用者確認的必須確認；Skill 說明介面行為，系統框架再加一層強約束。

（編輯觀點：這套「雙保險」是訪談裡最具體的制度設計——它承認 Agent 只能以助理身分辦事，不能替使用者行使權利。）

帶走三件事

生態要自己談。授權與接入邊界，不是模型變強就會消失。

記憶的難點是取捨。什麼不記、什麼時候不提，比存多少重要。

穩定度要拆到原子能力。上限靠模型，下限靠一條條可測的環節。
