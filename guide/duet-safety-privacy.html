煞車裝在模型之外：Claude Duet 的安全、隱私與資安設計

30 秒版本

Claude Duet 是研究預覽中的 agent：用一台雲端電腦替你做事，關掉 app 仍持續運行——讀收件匣、草擬回信、訂東西、跑例行公事。官方這篇說明它如何不失控：寄可能敏感的訊息、付款、刪除之前，一律先展示動作、目的地與完整內容（含每位收件者），等你批准；每個動作另有跑在模型之外的自動檢查（沿用 Claude Code 的 auto mode classifier），網頁裡藏的指令無法影響判斷。憑證與瀏覽器整組與模型隔離，密碼以單次金鑰加密直送雲端瀏覽器；購物用一次性卡號。官方也承認這些防護仍會漏判或誤判，會持續迭代。

  • 會在你不在場時行動的 agent，第一道設計題是「何時停、何時問」：敏感動作先展示、後批准，部分動作連「不再詢問」都不適用。
  • 安全檢查與憑證都放在模型碰不到的機器上：分類器獨立運作、密碼單次金鑰加密——抗 prompt injection 做在結構裡。
  • 證券交易、帳戶間轉帳、動他人帳戶即使你批准也不做；分類器會漏判也會誤判，官方只讓它與批准機制並用。

本文聚焦安全、隱私與資安；Duet 產品本身（何時主動開口、何時請示的設計）另見產品發布篇導讀。

先請示，而且要問得剛好：批准機制與審批疲勞

Duet 能使用你選擇連接到 Claude 的所有 app 與服務，並在你關掉 app 後持續運行——風險正來自這裡：會在你不在場時行動的 agent，必須知道何時停下來問，而且要問在對的節奏上。原文的設計：在寄出可能敏感的訊息、付款、或刪除任何東西之前，Duet 會展示動作、目的地與內容，包括每一位收件者，然後等你批准。每個動作旁邊另有一道自動檢查，建構在 Claude Code 的 auto mode classifier 上、為 Duet 延伸——它評估動作是否符合你的意圖，且刻意跑在執行工作的模型之外，藏在頁面裡的指令無法影響其結果。

原文的邊界可整理成三層（編輯歸納）。有些動作即使你批准也不做：證券交易、銀行動作（如在帳戶間移動資金）、存取他人帳戶。有些步驟不適用「不再詢問」——無論你批准過多少次：付款或匯款、刪除訂單、建立帳戶。在你離開時跑的例行公事（routines）適用同樣的防護。官方也花大量時間校準請求批准的頻率：審批疲勞是嚴重問題，太多請求會教人有時未經充分考慮就連點跳過。購物另有專屬通道：以 Stripe Link 等錢包的一次性卡號支付，限該商家與金額，你在 Link app 裡看到品項與總額後批准——真卡號不會交給 Duet，也不會交給商家。

這些設計有前傳。2025 年官方發布 safe and trustworthy agents 框架——把人放在控制位、把隱私與安全互動當基本要求；之後又寫過「為什麼沒有任何單一防線就夠」「為什麼模型內的防護無法獨立存在」。加上營運 Claude Managed Agents 基礎設施的經驗，Duet 以同樣方式把憑證與 agent 分開——這篇等於把框架落到一個替你行動的 agent 上。

寄出去的每則訊息，先過一道獨立分類器

一個會讀你信箱、替你寄信的 agent，時時都在決定「哪類資訊該去哪」。原文舉例：請 Duet 寄每週 recap 給團隊，它應該只放每個成員都已有權限看到的內容，絕不夾帶私人細節——例如你的績效考核對話。做法是一個新的安全分類器，獨立於主模型運行，在每則訊息送出前檢查是否含潛在敏感資訊；官方把這類資訊分為兩級處理。被任一級擋下時，Duet 可以決定改寫訊息、去掉敏感內容，再交給你批准。

官方對成熟度說得直白：Duet 還在 research preview，這些防護偶爾會漏掉該擋的、也會誤傷無害的訊息。正因如此，分類器只與前一節的批准機制並行運作——由批准機制守住「你控制 Duet 用你的名義寄了什麼」這一層；分類器則隨使用樣貌的累積持續迭代。

憑證與瀏覽器隔離：模型永遠看不到密碼

這是全文最結構性的一節：Duet 從頭到尾看不到你的密碼、瀏覽器 cookie、已連接 app 的登入 token，也不能把它們存進記憶。這些憑證只經過模型無法存取的獨立機器，掌管動作的批准與安全檢查也跑在那裡。具體流程：網站要密碼時，你在 Claude app 內的表單輸入；表單以一把單次金鑰加密——金鑰只存在安全的雲端瀏覽器機器上、僅供這一次使用——加密後的密碼原封不動交給瀏覽器、由瀏覽器鍵入網站。模型看不到密碼，無法儲存、也無法複述。下一步（即將推出）是 1Password：Duet 發出憑證請求、你在 1Password 裡批准，憑證直接交給瀏覽器，同樣不經過模型。

官方還點出釣魚攻防的兩個改變：其一，Duet 不替你保管憑證，所以無法被釣出密碼；其二，登入表單本身也是釣魚標的——Duet 的登入表單只會在 app 內、你主動要求的登入時出現，絕不會以連結、簡訊、郵件或 claude.ai 以外的網站送達，在其他地方索取密碼的「Claude Duet」都不是正版。

看得見也管得住：任務頁、開關與記憶

透明度落在任務層級：Duet 做過什麼、正在做什麼都在任務清單上，每個任務有獨立頁面，且可以在任務中途轉向（steer）。對話紀錄與記憶會保留、用來在任務之間延續脈絡，直到你刪除或重置；刪除帳號會清掉 Duet 儲存的一切。

已連接的 app 直接沿用，且開關同步：在一處關閉、兩處同時關閉。中斷連接後，新的存取即刻停止，但 Duet 已經學到的內容會留到你自己重置記憶為止（app 設定裡隨時可做）；它也會使用你 Claude 帳戶的記憶，先前對話裡記住的細節同樣可見。

帶走三件事

煞車要裝在模型之外。抗 prompt injection 的關鍵不是叫模型「別聽頁面裡的壞話」，而是讓判斷意圖的分類器、批准與憑證全部跑在執行模型接觸不到的機器上——用結構讓攻擊面失效，而不是靠模型自律。

「問幾次」本身就是設計題。官方花大量時間校準請示頻率，因為審批疲勞會把安全機制訓練成無腦連點——agent 的權限 UX 直接決定防護有沒有效。

預覽期的誠實也是設計。官方明說分類器會漏判、也會誤傷，所以只讓它與批准機制並用、不作唯一防線——從 2025 框架的「沒有單一防線就夠」一路貫穿到產品。
