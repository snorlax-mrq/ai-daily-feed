業務代理搬進 ChatGPT 與 Codex：Clay 的三檔模型分工

代理不只一隻Claygent 做研究與資料補齊，另有代理協助建流程、協調其他代理

問題不是沒有資料，而是資料太多卻不知道哪一條能打動客戶。

Clay 自稱「自學式營收引擎」：使用者先建公司與人名清單，再用代理補齊紀錄，最後套進 GTM play。

原文強調那個「range」：同一組模型要同時支撐背景研究與文案，也要支撐使用者直接互動的代理。

分工邏輯是按任務難度與成本切，不是按功能切——這點從三檔模型的說明方式就看得出來。

選擇上的關鍵不是分數，而是介面一致：Jeff Barg 說，不同價位共用同一套 Responses API 對他們很有吸引力。

他對 Sol 的評語是「對 GTM play 有很好的直覺，能建長跨度、以結果為導向的任務」——屬主觀評價，原文未附任何評測分數。

原文開頭把 Clay 定義為「自學式營收引擎」，但沒有解釋它怎麼自學；唯一接近的線索是結尾那句「代理從結果中學習」的願景。

兩隻代理的職責也分開寫：Claygent 負責研究、資格判斷、補齊與訊號偵測；另一隻負責幫使用者建流程、協調其他 Clay 代理。

原文沒說這兩隻怎麼互相呼叫，也沒說一個 play 裡會同時跑幾隻代理。

把能力送到業務已經在用的地方

原文舉的用法很具體：業務把自家系統與公開資料集併起來看，決定該怎麼講產品價值。

Jeff Barg 對成效的說法是「客戶很愛用 Codex 做銷售上的各種任務」、「最好的業務被賦能最多」——客戶案例的自述，無第三方驗證。

ChatGPT 外掛他給的說法是「很成功」，同樣沒有數字。

下一步方向是語音與 inbound：用 GPT-Live-1 以聲音操作 Clay 與 Codex，並開發能直接向潛在客戶展示產品或服務的代理。

他也提到 Decisions API 是另一條把模型接進 Clay 的路，但原文沒有給出具體用法。

連開發流程也被同一個模型吃掉

這段值得注意的地方不在工具，而在驗證被納入代理的工作範圍：不只寫，還要跑、要記錄、要交付。

Clay 的方向是把 GTM 流程從頭做到尾，讓代理從結果中學習、愈跑愈好——目前是宣示，不是已完成的能力。

（編輯觀點：客戶案例的重點通常是「代理被放在既有工作流的哪一格」——Clay 選的是業務與建置者各自已在用的那一格。）

原文沒有揭露 Clay 的用量規模、成本節省或成交率變化，全部成效敘述均為公司與受訪者自述。

帶走三件事

分檔不是省錢而已。難題與成本敏感工作本來就該分開配。

外掛是通路策略。把代理送進業務捨不得離開的介面。

驗證也交給代理。寫完就跑、就記錄，才叫閉環。
