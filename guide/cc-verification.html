驗證迴圈：能並行幾個代理，取決於證據

驗證迴圈不是品質加分項，而是能不能大量委派的開關：有了它，審查從逐份讀 diff 變成看證據。

沒有迴圈，你得一一看過產出，同時只敢開一、兩個 Claude；有迴圈，原文說可跑到數十甚至數百個。

驗證成本也反轉了：測試、benchmark、規格、端到端實跑，過去貴，現在可請代理生成；生成後它們是軟體，重跑不太燒 token。

值不值？內測針對結構化檔案生成：另找評分者依 rubric 檢查，比標準提示迴圈最多提升 10 個百分點，難題收益最大。

三種測試：能被騙過的檢查沒有價值

只能投資一種，原文選端到端：要嘛功能整個能用，要嘛不能用，有明確完成判準，也講得出壞在哪一步。

類型查什麼抓什麼錯代價
端到端真實使用者流程：加入購物車→結帳→確認頁功能整個壞掉；並能指出哪一步壞慢、較易 flaky；重的測試放提交前跑
性質你認為不可能失敗的敘述：往返編碼、不變量、冪等、等價人與代理都想不到的邊界輸入要自寫性質與挑套件（fast-check／Hypothesis／proptest），每次生成數千筆輸入
差分新舊系統餵同一批輸入，比對結果遷移造成的行為漂移或破壞性變更舊系統得跑得動；要正規化空白等雜訊，並維護核可差異清單

端到端難騙，是因為它不接受「看起來對」：整條流程跑得完才叫過，跑不完就一定有東西壞了。

單元測試快、不易 flaky，卻可能全過而功能仍壞——因為代理與那份測試都沒掌握完整任務。

端到端的關鍵是給代理手和眼：用 skill 啟動、操作、檢視真實系統，工具可以是 CDP、模擬器或 API harness。

feature map 也能當指南兼評分 rubric：它通常已用使用者視角列出路徑、快捷鍵、selector 與預期結果。

性質套件會在背後生成數千筆輸入試著推翻你的敘述，且那些邊界輸入不帶寫碼代理的偏誤。

差分特別適合大規模遷移：功能預期不變，舊系統就是現成的判準（原文稱 oracle）。

性質測試贏在偏誤不同：邊界輸入不是寫那份碼的同一個代理想出來的。改寫時尤其好用，因為規格早已漂離實際行為。

先修失敗模式，再談關卡

兩個失敗模式要先修：flaky 測試會訓練代理重跑，而不是去修壞掉的程式；測試太慢，代理就少跑幾批，事後也難定位。

團隊的規矩很硬：不准跳過測試、加 sleep 或重試到過；找不到根因，就刪掉它並寫下原因。

團隊講的驗證是「把改動跑起來」：repo 裡放 verify skill，Claude 提交前自己開 app 或模擬器；檢查連三輪沒過才停下來找人。

verify skill 放在 .claude/skills/，越靠近相關程式越好；原文建議它要是可靠的 smoke test harness，請 Claude 自己迭代、壓測。

檢查按 diff 觸發：清單每項都有可從 diff 讀出的條件，Claude 只跑命中那幾項，通常 3 到 10 項，不必背下所有事故。

便宜的先跑：Claude 開 PR 前自己跑測試、build、linter；先推再測，等於花掉共用的審查與 CI 時間。

最關鍵是問責：改動不能修改自己的裁判。Code Review 只從 base 分支讀 REVIEW.md；過期 commit 上通過的審查不算數。

新關卡先開 observe，只記錄「本來會被擋」的提交；確認誤擋再轉 enforce。同一 session 被擋兩次後放行一次，免得卡死。

原文也不靠疊評審：在主要評審上再加一個更貴的，通常不如把主要那個調好，並用 REVIEW.md 寫明這次該看什麼。

規則的門檻是：至少在兩個 PR 出現、且能從 diff 看出；三個代理先試著反駁，再由人核准。規則是會腐壞的，得定期清。

評分者本身也要被評分：repo 還原到當時狀態、只給一句答案，正確描述該 bug 的發現才得分；召回率分三段量：原始發現、驗證後、最終審查。

評分也有分級：Important、Nit、Pre-existing；pre-existing 表示 bug 原本就在，不該算在這次改動頭上。

迴圈成熟後，重心從讀每一份 diff，移到定義什麼叫完成、然後看證據。

（編輯觀點：這套的固定成本在維護——39 項清單、規則與 verify skill 都得有人養；不養，迴圈只剩形式。）

帶走三件事

先有迴圈，再談並行。沒有證據可看，一兩個就是上限。

測試要難騙、要快、要穩。flaky 教代理重跑，慢測試教它少跑。

裁判不能被改動改。規則鎖在 base 分支；漏掉的 bug 寫成新規則。
