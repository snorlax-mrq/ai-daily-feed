Obsidian 當記憶、Hermes 當操作員、MiniMax M3 當推理引擎——讓 agent 住進筆記庫形成回寫迴圈；成效全是作者自報的單人樣本。

他為什麼挑 M3：一個失敗模式，四個症狀

開場先講筆記軟體為何不夠：經典 PKM 有三種死法——筆記寫一次就不再更新、AI 對話聰明但每次從零開始、認真工作的 context 不斷掉出視窗。他要的三件事：本地可連結的圖譜、住在圖譜裡的 agent、能在巨大真實 context 上推理的模型。

他不是按 benchmark 選模型。2025 年試過的模型都卡在同一個失敗模式：摘要單篇沒問題，一旦要讀十篇筆記、對照 MOC、再寫回新筆記，就斷線。

他要的是一個能讀整座 vault、日誌與一批新文章的模型，不想自己黏 RAG 管線；試用幾個月後 M3 留了下來——長 context、多模態、agentic（作者描述）。

症狀固定四種：摘要局部對但全域錯、引用檔案裡不存在的專案、用了別套 taxonomy 的標籤、編造不存在的 wikilink。他的結論：「模型很聰明，工作流比模型大」。

三個對症點指向同一件事：整座圖譜要能一次進 context，而且留得住。他說 M3 是試到第一個做得到的（自報）；表內百分比全無量測方法。

迴圈與邊界：資料夾就是權限表

每圈五步：人往 Inbox 捕捉 → Hermes 讀 vault → 把相關筆記集送進 M3 → M3 重構、標籤、連結 → Hermes 以乾淨 markdown 寫回。寫回的筆記成為下一圈的 context。

兩條原則撐起地基：「值得留的東西先進 Obsidian；agent 做出有用的事，就要變成一則筆記」。Hermes 的位置在 vault 與模型之間：把圖譜變成可操作的東西，而不是取代 Obsidian。

他的話：「那個迴圈——不是一次性對話——才是真正的產品」。模型分工照同一邏輯：小模型管改檔名、找字串，M3 只接需要整座圖譜的活。

邊界用資料夾講清楚：人寫 Inbox／Daily／Reading，Hermes 只准彙整進 Projects／Reviews／主題資料夾——不寫 YAML 也有權限界線。

他最常跑的 job：文章丟 raw/，M3 產 5 段式筆記，從約 41 個標籤選主標籤、寫 8–12 條指向既有筆記的 wikilinks、點名要更新的 MOC；200K 模型或許四項中三，M3 全中（自報；原文僅明列三項成果卻稱四）。

排程補上非同步：每天 08:00 摘要昨日、週五出週報、每天掃孤兒筆記、每晚把 highlight 原子化。他的對比：「聊天回答會消失，排程的筆記維護會複利」。

落地路徑本身可驗證：CLI 裝在 Linux／macOS／WSL2，另有 macOS／Windows／Linux 的 Desktop 殼；hermes doctor 體檢、hermes model 選模型、hermes setup 開機。
