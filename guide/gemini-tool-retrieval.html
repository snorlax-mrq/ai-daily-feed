Tool Retrieval 把工具庫拆成兩層：模型永遠看得到每個工具的名字與描述，參數 schema 則等真的要用才載入。

原文的算術很直白：代理接上數十、甚至數百個工具後，每次請求都送完整參數 schema，輸入 token 與延遲一起膨脹。

候選清單一長，工具挑選的準確度還會下降。原文把三件事並列，來源只有一個：每次重送整座工具庫。

參數 schema 指的是工具參數那份 JSON 定義；它通常比名稱與描述長得多，被用到的頻率卻低（編輯推論）。

開啟只要兩個動作：tools 陣列裡放一個 tool_search，再把想延後的工具標上 defer_loading: true。

延後的工具沒有消失。模型照樣看得到每個工具的名稱與描述，知道有哪些可用，只有參數 schema 被擋在 context 外。

模型真的要用時按名字點名，API 補進完整 schema，模型再發出 function_call——三步都在同一個請求裡完成。

原文範例是一筆退款：50 多個延後函式裡，模型只挑中 issue_refund，帶上 order_id 與 amount 直接呼叫。

這三步會以 tool_search_call、tool_search_result、function_call 出現在 interaction.steps。工具名字或描述寫壞，就從這裡查。

名字與描述因此變成新的槓桿：schema 藏起來之後，模型只剩這兩樣線索可以挑工具（編輯推論）。

不必全部延後。原文說可以把最常用的工具留在前面載入，只把長尾標成延後。

延後是逐個工具決定的旗標，同一個請求裡可以一部分延後、一部分照舊全送。

這也讓前綴快取接得上：延後的 schema 不佔 prompt 開頭，載入的 schema 落在對話後段，快取前綴每回合都相同。

誰來執行搜尋：Gemini 端或你自己的註冊表

伺服器端模式不用自己寫查詢參數；要定義搜尋參數的，是客戶端模式。

沒有索引要建、要託管——原文特別點出這句：搜尋在 Gemini 端跑，你不必先做一份離線索引。

代價寫得很清楚：客戶端檢索每次搜尋多一個往返，因為查詢在你的應用裡跑。

換來的是彈性——工具不必事先宣告，使用者中途接上一個整合，新工具可以當場出現。

遠端 MCP 伺服器能整包延後：對 mcp_server 標 defer_loading: true，該伺服器暴露的每個工具都按需載入，不必逐一列出。

帶走三件事

省的是 schema，不是工具。名字與描述照送，模型才知道有什麼可挑。

常用工具別延後。前載常用、延後長尾，才不會每次多繞一趟。

省多少要自己量。原文只說大型工具庫通常划算，一個百分比都沒給。
