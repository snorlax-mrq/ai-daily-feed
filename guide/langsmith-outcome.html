代理花費：合併 PR 才是計價單位

導讀

原文：LangChain 官方部落格〈LangSmith for Coding Agents: Now track spend by outcome〉——產品公告，說明把 coding agent 花費綁到 PR 的歸因機制、儀表板與四種用法

LangChain·2026-11-18 發布·2026-11-19 收錄· 閱讀官方原文

340 億美元2026 年企業 AI 應用支出中「寫程式」類別的規模（原文以連結引用 Menlo Ventures〈2026: The State of Enterprise AI〉）
5 種代理Claude Code、OpenAI Codex、Cursor、VS Code 的 GitHub Copilot、Deep Agents
3 種 PR 狀態open／closed／merged 分開計價，沒開出 PR 的花費另歸 unattributed
public betaLangSmith Cloud 公測；coding agent 的 trace 照一般用量計費

outcomes 把 GitHub PR／GitLab MR 連回產生它的 thread：一個合併 PR 花多少、多少錢完全沒產出，第一次變成可查的數字。

原文給的理由很直白：寫程式是企業 AI 應用支出的最大類別，2026 年達 340 億美元（原文以連結引用 Menlo Ventures〈2026: The State of Enterprise AI〉），但多數工程主管說不出這筆錢買到什麼。

過去團隊只能看用量分析與 AI 消耗量，看不到 token 到底產出了什麼；要回答 ROI，得同時有跨人跨隊的花費視角，加上一條把花費接到成果的線。

LangChain 自己先撞到這面牆：內部 coding agent「Robin」的花費開始上升，這也是他們去做 model router 的原因之一。

歸因規則要吃得下兩種現實，否則數字會失真：一個 thread 開出多個 PR，或一個 PR 要好幾個 thread 才完成，都要算得進去。

新儀表板：以代理為中心，coding agent 是第一種型別

LangSmith Agent Platform 改成繞著代理轉：每個代理有自己的紀錄，並屬於某個 agent type，型別決定它的儀表板顯示什麼、接哪些資料、怎麼被評估。

coding agent 是第一種專用型別，它用 PR 呈現成果——原文稱這只是「工作有用」的訊號之一，不是唯一判準。

舊版只有逐條 trace 的單價，適合手動除錯，看不到全隊趨勢；新頁面把成本彙總、綁到 PR，任一 KPI 都能點開成時間趨勢。

團隊不會只跑一種代理：有人用 Claude Code，有人用 Cursor 或 Copilot，平台團隊用 Deep Agents 自建。LangSmith 全部收進同一頁，不必在各家後台拼數字。

上線方式是三步：為每個代理裝外掛、連上 GitHub、打開 overview 頁；Claude Code 是在 session 裡跑三個指令。

舊指標答不了的四個問題

問題舊指標（用量／消耗）outcomes 之後原文承認的盲點
錢花在哪每人、每隊的 token 與消費總額花費落到 PR，可依歸因成本排序出最貴的 PR單一 PR 可能包含多個 thread 與多輪對話，長 thread 會把成本集中在同一個 PR
買到什麼答不出 token 產出什麼合併 PR 的數量與單位成本合併 PR 是有用訊號，卻不是唯一的有用工作
沒產出的花費混在總量裡，看不出比例依 PR 狀態分帳；沒開出 PR 的歸 unattributedunattributed 可能仍是探索、審查這類有價值的工作
為什麼貴只有單條 trace 的價格反查 thread、用到的模型、GitHub 使用者與工作類型值不值得，還是得人進去看那一串對話

三個 PR 狀態分開計價，是這頁最實在的地方：關閉與未合併的花費，不會被合併 PR 的平均值藏起來。

unattributed 不是垃圾桶。原文說審查程式、追查問題本來就不一定開 PR，點進去能看到那些 thread 究竟做了什麼。

work type view 替每個 thread 貼工作類型（feature、bug fix、investigation、code review），列出各類的 thread 佔比與花費佔比。

它同時解釋了 unattributed 從哪來：審查與調查類的 thread，通常不會各自開一個 PR。離題的定義則由各組織自訂，例如只做後端的團隊可把「寫行銷文案」標成 off topic。

頁面還列出代理呼叫了哪些 skill、最貴的 PR 是哪幾個、成本如何隨對話長度放大。每個指標都能點回背後的 thread 與 session，這是它與一般花費報表最大的差別。

打開那些貴的 thread，原文舉例兩種常見原因：對話越拉越長，或在小修補上用了最貴的前沿模型。原文建議把這類差異找出來，變成團隊共用的做法。

這些數字怎麼用：四種判斷

用途看哪個數字換到什麼判斷
教練依歸因成本排序的 PR，往回開到 thread、模型與 GitHub 使用者同類工作有人便宜很多，差異出在哪個習慣
換模型改動前後的「每個合併 PR 成本」，或新舊供應商並跑對比新模型的成果值不值它的價；子代理換小模型省多少
治理 skillskill 呼叫與 thread 長度、是否導向合併常出現在長而貴的 thread，可能是指令害代理多繞幾輪
財務對帳每個合併 PR 成本，並排 unattributed工程與財務終於看同一組數字，而不是兩套說法

長 thread 是花費集中地：每個新 turn 都重送整段上下文，成本隨長度累加。原文建議一個任務開一個新 thread，並引用 Anthropic 的 Claude Code 成本指南——任務之間清掉上下文。

推廣之後，同一個檢視就能驗收習慣有沒有改：長 thread 佔的花費比例，有沒有真的降下來。

換模型要看的是「每個合併 PR 成本」，不是單價：單價降了、合併變少，等於沒省。

skill 也一樣：先給幾位工程師試，再拿用了與沒用的 thread 比成本與合併數，而不是憑感覺全面推。

原文的提醒值得記住：每個合併 PR 成本偏高，不代表做法有問題——unattributed 裡可能裝著探索與審查，那是有價值但開不出 PR 的工作。

（編輯觀點：這是廠商自家產品的公測公告，「能回答什麼」由 LangChain 定義；單位成本能不能比，還取決於團隊開 PR、合 PR 的紀律是否一致。）

帶走三件事

沒開出 PR 的花費不是零。先看 unattributed 裡裝的是什麼。

合併 PR 是可計價單位，不是唯一價值。審查與探索本來就不開 PR。

換模型先看每個合併 PR 的成本。單價降、合併少，等於沒省。
