只讀 diff 的審查器先天吃虧：看不到 diff 外的 import 與 helper，也無法證明懷疑的 bug 真的會炸。

OpenRouter 的做法是把變更搬進沙箱，讓模型自己寫檢查、自己跑；跑得出來才標 confirmed。

未確認不等於沒問題。連線沒關、競態這類要靠人判，原文把兩類分開陳列，不讓它們混在一起。

補丁也不直接落地：模型送 patch，腳本先套在本機暫存副本並回報結果，模型再修，才輪到你決定 --apply。

原文特別註明，沙箱裡跑的還是原始碼，所以 --apply 之後要自己再跑一次測試，才算真的修好。

報告預設落在 .git：裡面有不只 findings，還有完整 shell 輸出與你的程式碼片段，放那裡才不會被 commit。

四個工具各管一段

工具在流程裡做什麼原文限定語
Files API上傳變更後完整檔案、context 檔與 diffbeta；每檔 100 MiB、每工作區 10 GiB，不另計費
openrouter:shell托管 Linux 容器，把上傳檔複製到家目錄再跑指令beta；僅 Responses／Messages API，Chat Completions 回 400
openrouter:apply_patch模型以 V4A diff 提議 create／update／deletebeta；只驗語法並回送錯誤，實際寫檔留給你的程式
submit_review收尾時回傳結構化 findings函式工具＋嚴格 JSON schema，非 text.format

→ 可橫向滑動

三個伺服器工具都還在 beta，且只支援全域端點；第四個 submit_review 是函式工具。

為什麼收尾要用函式工具？原文實測 haiku-5.5 同時帶工具時，text.format 的 json_schema 沒被強制，答案會變散文。

上傳後的檔案在沙箱叫「檔案 ID 末八碼＋原檔名」，所以提示詞得寫死重建目錄的 cp 指令，否則模型找錯位置。

補丁路徑由模型給，腳本用 inside() 解析後拒絕 repo 外的路徑；檔名進 shell 前一律 quote。

原文踩到的坑比功能更值得抄：長請求偶爾被丟包，所以全部改串流並只重試一次；Python 預設的 User-Agent 會被 Files API 回 403。

還有一個型別坑：原生的 apply_patch 在 Claude 上每次都驗證失敗，得改用 openrouter:apply_patch。

每份補丁要立刻套、立刻回報。原文試過只回「已存」，結果模型把同一份補丁重送兩三次。

四款模型：差在敢不敢斷言，也差在補丁對不對

同一個植入五個 bug 的變更，每模型三次、預設參數與 --context 測試檔；「找到 bug」分母為完成場次×5。費用單位美元，原文未給變異數。

差別在敢不敢斷言：Sonnet 三次都把五個 bug 的補丁修到全過，Haiku 只有一次。

被刪掉的 conn.close() 成了分水嶺：Haiku 與 Sonnet 判 unconfirmed（Haiku 漏過一次），Luna 從沒回報但有一次補丁順手修好。

DeepSeek 兩次都確認它，其中一次靠數 /proc/self/fd 的檔案描述符前後差異。

DeepSeek 另有一次跑滿八回合只顧重送補丁、始終沒交報告，以退出碼 2 收場，花了 0.034 美元。

補丁要自己讀。Haiku 三份補丁有兩份把 total_revenue 改成取 tuple，反而弄壞呼叫端。

示範環境是 Python 3.11.14 加 SQLite 3.50.4，有 unittest 沒有 pytest；植入五個 bug 後，兩個既有測試照樣通過。

成本結構反直覺：沙箱每秒 0.0001 美元，從第一道指令計費到回應結束，慢模型即使 token 便宜，沙箱費仍較高。

原文的數字：Haiku 的沙箱費 0.0074 至 0.0159 美元，較快的 Sonnet 是 0.0047 至 0.0068 美元。

純看 diff 的 Chat Completions 審查器（Haiku 5.5）約 0.001 美元一次；換成跑得動程式，貴 10 到 40 倍。

三種收場，別把「沒跑完」當通過

門檻預設 high，只有安全漏洞、資料遺失、核心行為壞掉才擋；其餘留在報告裡給人看。

掛成 pre-push hook 時，它比對的是工作區與基底分支，無關的改動得先 commit 或 stash。

--no-verify 能跳過本地 hook，所以 CI 還是要跑一次；fork 的 PR 一律跳過，因為那份工作會把程式碼送出去。

沙箱預設沒有外網，pip install 會失敗；要跑第三方套件的檢查，得自己開 network_policy 白名單。

檔案會上傳到 OpenRouter 工作區並送到模型供應商，機密程式碼不該丟進去——原文寫得很直白。

原文註明：CI 要用基底分支的 review.py 來跑，PR 才改不動自己的守門人；但那份 workflow 作者並未在 GitHub Actions 實跑。

模型仍會漏 bug、誇大嚴重度、寫出壞補丁。原文的建議是：confirmed 當強訊號，unconfirmed 當給人看的備註。

帶走三件事

先讓它跑得動，再問準不準。沒有重現證據的 finding 只是猜測。

補丁一律當草稿讀。原文實測有模型把 bug 修成另一個 bug。

沙箱會把程式碼送出去。機密 repo 不進第三方沙箱，這是前提。
