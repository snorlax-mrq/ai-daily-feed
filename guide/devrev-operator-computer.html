這是一篇客戶案例訪談。最值得抄的不是用了哪個模型，而是把「動手」與「遞球」拆成兩個代理。

一個負責把事做完，一個負責把球交好。（編輯推論：前者比成功率，後者比交接後人能不能立刻接手，兩種能力要的評測不同。）

把評測對象換成「模型＋公司情境」

原文沒提公開 benchmark；重點是 DevRev 自建 Enterprise-Bench，測的是模型與「餵公司情境、控權限、管動作」那層軟體的組合。

壓力原文描述公開評測可能漏掉的地方
資料有多版本資料具有多個版本答案該引用哪一版，取決於流程而非語意相似度
資訊散在各系統資訊分散在不同系統要跨系統拼答案，單輪問答看不出組裝能力
存取依角色能否存取取決於當事人的角色同一個問題，不同人該得到不同答案

（編輯觀點：第三欄是編輯推論。原文只列出三項壓力，沒有解釋為何公開 benchmark 不夠用。）

Bashir 對 GPT-6.1 Sol 的評語很節制：效能好，且在「要聽懂請求細節」與「要快、成本要能持續」之間取得平衡。

原文沒公開 Enterprise-Bench 的題目數量、評分方式，也沒給任何分數；唯一證據是 CTO 的說法。

harness 是 DevRev 自己那一層：接公司知識、管權限、決定代理能採取哪些動作。（編輯推論：模型換代時，這層可以留著。）

開發端已經全面換工具

訪談中最具體的一段不在客服，在內部開發：DevRev 工程團隊全面改用 Codex，並退掉 Cursor 授權。

Bashir 的說法是先讓工程師試多套工具、後來自然收斂；「開發者只想要最好的工具，騙不了他們」是他給的理由。（DevRev 自報，無第三方驗證）

銷售工程師則用 GPT-6 Astra 做國際展場的 demo——同一批模型，一邊跑產品、一邊跑銷售流程。

（編輯觀點：把 Codex 寫進客戶案例，對 OpenAI 是雙重收益——既證明企業採用，也順帶推銷自家 coding agent。）

下一步他們想要的是「幾秒內自己跑完」：把難用固定規則描述、又依賴變動資訊的判斷，交給 Decisions API 與 Ultrafast 處理，不必每一步都做深度推理。

可逆與可追溯，是企業代理的門票

Bashir 把三個條件當成產品設計前提：動作可逆、答案指回來源、團隊能控制代理可執行的動作。（CTO 自述，無第三方驗證）

Agent Studio 讓使用者在對話中描述工具行為，部分行為用固定規則釘死。（編輯推論：這等於在提示與程式之間留一個可審核的夾層。）

（編輯推論：這三條其實在回答採購單位真正的問題——錯了怎麼收回、事後怎麼查、誰准它做的。）

訪談裡模型提供推理與可靠性，速度與成本則是能不能服務真人的門檻——三者在同一句話裡並列，不是附帶條件。

自助服務的邊界

Bashir 點名目前只算起點的三件事：查知識庫答案、升級方案、退款。（編輯推論：這三件都是規則明確、結果可逆的動作。）

他真正的目標是更長的請求也能自己跑完，同時保持可追溯、有權限、可回復。

（編輯推論：若每個決策都要做深度推理，自助服務的成本會隨筆數線性上升。）

帶走三件事

拆兩個代理，比做一個全能的好管。動手與遞球分開，權限也分開。

評測要含公司情境。只比模型分數，挑不到能上線的組合。

先問可逆與追溯。不能收回的動作，不該給代理自己決定。
