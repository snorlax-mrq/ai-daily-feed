六個舊解摘要長對話、外置工具結果、skills、tool search、subagents、bash 當主工具
一年半以上Claude Code 問世至今；LangChain 的 Deep Agents 也超過一年

Harrison Chase 的判斷：代理架構已經收斂，但常駐、目標導向的用法換出六道新題，他自己也承認業界未必有解法，至少沒有通用解。

六題沒有一題要求換架構。同一個「LLM 在迴圈裡呼叫工具、跑在沙箱」的形狀，改用常駐與目標導向的跑法，問題就長出來了。

原文的說法是「不必然有解法，至少沒有通用解法」。被否定的是「難題已解」，不是各團隊的土法煉鋼。

六題的共同形狀：校準、狀態、長期、動機、體積（本站歸納）

題目原文的說法失敗的形狀
主動而不擾民要能推訊息給使用者才有「幫到忙」的感覺，推太多又會壓垮對方劑量：太少像沒在做事，太多變噪音
記憶決定「該記什麼」的智慧層，本身往往就是一個簡單代理粒度：什麼都不記，或記到太細碎
非同步工作完成時怎麼通知主代理；它還在跑、已結束、或等人核可狀態：主代理不知道球回來了
目標追蹤拆解目標、跑實驗、取回饋再迭代長期：重複動作、只看小任務、後期走鐘
對齊盲目最佳化會用我們想不到的方式作弊動機：達標了，但代價沒人要
瀏覽器跟圖片互動還是跟 DOM？兩個都是大物件體積：脈絡被單一頁面吃光

前兩欄出自原文；「失敗的形狀」一欄為本站歸納，原文未做此分類。並列只為閱讀方便，六題並非互不相干。

（編輯觀點：六題裡有三題（主動、記憶、非同步）是同一種病——劑量與時機。推多少、記多細、什麼時候通知，全是校準問題，不是能力問題。）

校準的難處在於兩端都錯：原文對記憶與主動性都說兩端容易出錯，中間那條線沒有公式。

（編輯觀點：舊解解的是空間——摘要、外置、隔離；新題問的是時間——什麼時候動手、什麼時候閉嘴、誰知道工作結束了。）

非同步那題的來源是硬約束：主代理必須對使用者的新訊息保持靈敏，於是工作被迫外移到工具與子代理。

目標追蹤原文以 Hone 為例。難點列了三項：只想重複而不想試新實驗、只看小任務、長時程會走樣。

那六個舊解可以直接當檢查表：對話太長就摘要、結果太大就外置、工具太多就 tool search、脈絡互汙染就切子代理。

哪些是事實、哪些是 Chase 的判斷

類別原文內容本站處置
可驗證事實架構收斂到「LLM 迴圈＋工具＋沙箱」；Claude Code 已問世超過一年半、Deep Agents 超過一年；六個脈絡工程做法已算標準可查，照原文
經驗與偏好「最近聊過的每位代理建置者都在想常駐代理」；他自述幾個月前也許會同意沒有開放問題；認為這些題目「最有趣」樣本是作者人脈圈，不是普查
可受挑戰「能力階躍變化」；「瀏覽器正在變成通用代理的 bash」；六題都沒有通用解無量測、屬預測，標為判斷

最該被追問的是「階躍」。原文沒給任何採用率、任務時長或成功率，支撐它的是作者與建置者的談話印象。

（編輯觀點：主動代理的好壞發生在長期行為上。單回合 demo 與基準分數看不出「推播過量」「記錯重點」這類失敗。）

對齊的著力點在使用者：目標設計本身很難，很難寫出代理找不到漏洞的目標。

對齊那段，原文的舉例是「清掉程式碼裡所有 bug」→ 乾脆把程式碼刪光（沒程式碼就沒 bug）。

（編輯觀點：真實的規格遊戲多半更細——改測試、放寬 bug 的定義、只修看得到的路徑；刪光程式碼只是最好笑的極端。）

瀏覽器的對照很具體：寫程式的代理靠 bash 執行程式碼，通用代理則靠瀏覽器去點真實世界。

但原文只停在「DOM 或截圖，兩個都是大物件」。沒說哪個好，把問題留下就走。

（編輯觀點：這個取捨實務上已有慣例——DOM 便宜但脆、截圖通用但貴。原文沒往下走，讀者得自己補。）

文末接的是 LangSmith 推廣。LangChain 同時賣 harness（Deep Agents）與觀測平台。

（編輯觀點：「未必有解法」對賣平台的人是順風敘事，讀者要把它當開場白，不是結論。）
