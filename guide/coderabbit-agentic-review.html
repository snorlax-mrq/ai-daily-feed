一句話：便宜模型鋪量、貴模型做決策，再用擅長攻擊的模型掃自己的程式碼。

CodeRabbit 賣的是「驗證與信任 AI 產出程式碼」的治理層：審查、解釋，並決定哪些代理寫的變更可以上線。

共同創辦人暨執行長 Harjot Gill 的說法很直白：「每家公司採用編碼代理後撞到的第一個瓶頸，就是 code review。」

代理讓待審的程式碼變多，審查本身又得靠代理，於是成本結構決定架構：便宜的跑量、貴的做判斷。

這條線走過四代：第一款產品用 GPT-3.5 Turbo，GPT-4 才讓審查真的可用；o1、o3 是早期採用，現在換成 Luna 與 Astra 分工。

起點是一到兩個子代理做程式碼導航；現在低成本模型撐起平台各處的子代理，規劃與編排交給 GPT-6 Astra。

審查在雲端非同步執行，模型可以「想久一點」換取更強分析；這是 o1、o3 能被早期採用的前提，也和互動式工具的選型邏輯相反。

選型的尺是自己建的已知問題集：訪談當下 Gill 估計 GPT-6 Astra 命中其中 50%，在該基準上排第一（自報）。

Gill 對模型迭代的評價是「每次新模型發布、尤其推理模型，我們在大規模找問題的能力上都看到大幅提升」——這是客戶對供應商的表態，不是量測。

這把尺會自己長大：代理帶來新的錯誤類型，修好的地方又暴露出舊審查漏掉的問題。

20 倍交付的代價：整條交付線重做

原文對代價的描述比成效還多。Gill 的說法是「整個軟體交付流程得徹底重想」。

多個代理同時跑起來，被撐爆的環節才一一浮現；換模型只是起點，採用本身不是解法。

低風險變更改由 CodeRabbit 自動出貨，不必人簽核；人工核准的位置因此整段重排。

另有一支 Codex 驅動的 Slack bot，分流生產事故、Slack 訊息與客服單，必要時直接開一張待審 PR 回給人合併。

原文也提到把開發搬上雲端：減少本機機器的限制，並讓存取權與稽核的控管更強。

（編輯推論：20 倍沒有計算基準——是 PR 數、程式碼行數還是上線功能數，原文未說明；資料卡裡的 PR 數是 Gill 個人數字，兩者不能相乘。）

（編輯觀點：把核准權下放給自動化，前提是風險分級本身可信；原文沒給分級規則，也沒給誤放行率。）

→ 可橫向滑動

安全這條線起步更早：團隊在沙箱裡 clone repo、讓代理寫碼協助審查；近期改用 Daybreak 取用 OpenAI 的 Cyber 模型，對自家平台做內部滲透測試。

Gill 的說法是找到多個漏洞、一些「根本想不到會發生」的進階手法；原文未列漏洞類型或數量。

同一套能力變成商品 CodeRabbit Secure：促銷兩週、替用戶吸收 100 萬美元等值的深掃費用（原文 $1M），數千個漏洞已由客戶修掉。

掃描筆數與漏洞總數見上方資料卡，兩者都出自 CodeRabbit 自述；「深掃」的定義與計數口徑，原文沒有交代。

原文也沒給客戶名單、行業分布，或第三方對其審查準確度的評測；可查的只有該公司自建的基準。

往前看，CodeRabbit 要把驗證、排優先序、解釋、防護與核實都做成規模化服務，替代理產出的變更把關。

方向也寫在結尾：背景代理開始自己回應告警，人的工作會變成判斷哪些變更要做到完成。

帶走三件事

審查是代理化的第一道牆。交付出貨變快，待審量先爆。

20 倍不只靠模型。發布流程與審批位置也得跟著改。

自報數字先問口徑。「深掃」與「20 倍」原文都沒定義。
