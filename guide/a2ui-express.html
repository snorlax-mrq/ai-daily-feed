模型少寫括號：A2UI 把推論格式變成一個可替換參數

最多 3 倍Express 降低延遲，基準是 Direct JSON（Google 自報）
最多 80 倍改用 Jev 這類決策模型決定版面時的延遲降幅
最多 1/3token 用量（原文 up to 3× fewer），基準為 Direct JSON

原文的主張很直接：慢的不是生成式 UI，是逼 LLM 逐字吐出受 schema 約束的 JSON 樹。這一版把「模型輸出什麼格式」變成可替換的參數。

原本的設計很乾淨：client 用 catalog 宣告受信任元件當契約，agent 送出描述介面的訊息，renderer 負責畫。

壞就壞在初版要 agent 自己寫 JSON 傳輸訊息：每個大括號、每層巢狀都得自己生。

副作用比速度更麻煩：A2UI 被綁在「會輸出文字」的 LLM 上，接不進更快的 System One 決策模型。

一個參數，換掉 prompt 與 parser，不換協定

推論格式有兩半，都從 catalog 的 JSON schema 生成：一段教模型語法的 prompt，一個把回覆編譯成已驗證訊息的編譯器。

兩半同源，所以格式描述不出 catalog 沒有的元件或屬性。

換格式只動 prompt 與 parser；catalog、few-shot 範例、訊息格式、renderer 全不動。

API 只是一個參數：建立 generator 時傳 ExpressFormatFactory()，TypeScript 則放在第三個位置。

特殊用途也能自帶 DSL：原文說 agent builder 可換上任何一種 DSL 與對應的編譯器，SDK 負責讓它接得上既有的傳輸與 renderer。

取捨：Direct JSON 在 Python 與 TypeScript SDK 能逐塊串流，Express 收完整回覆後才編譯。

可用版本：Python a2ui-agent-sdk 0.9.0（PyPI）、TypeScript @a2ui/agent（npm）、Dart a2ui_agent 0.0.1-wip004（pub.dev）。Python SDK 另有 macros：模型只寫 OrderStatus("ord_42")，由 macro 去撈訂單並填值，畫面上每個值都直接來自你的資料系統。

模型要寫的東西：從 JSON 樹變成一行一元件

原文的對照很具體：Direct JSON 要模型連括號都自己寫；Express 只寫元件與參數，結構交給編譯器補回。

寫法在 Express 裡的意思由誰接手
一行一語句每行把一個元件指定給一個變數模型
變數名直接成為該元件的 ID編譯器沿用
位置參數依 catalog schema 宣告的順序對應屬性名，_ 跳過一格catalog schema
$/title把這個值綁到資料模型資料模型
Event("accept")宣告一個伺服器動作伺服器

原文的示範是通知卡片：surface 先綁三個資料欄位（description、icon、title），其餘每行一個元件。

兩顆按鈕各自宣告 Event("accept") 與 Event("decline") 的伺服器動作。

→ 可橫向滑動

形狀固定的畫面，換模型比換格式有效

有些畫面形狀是已知的：設定頁、結帳頁、確認頁。這類畫面不需要模型設計版面，只要在你預先定義的版型裡挑一個。

Jev（TypeSafe）是 System One 模型：它不生成文字，也不生成 JSON。

你送一個狀態與一組有型別的問句，它逐題作答；程式拿答案組出 A2UI 訊息，文字另由小模型寫。

原文的判準：這種畫面用不到 Express 提供的完整表達力。

評測基準：四種候選格式跑同一份 51 題，模型是 gemini-3.5-flash，思考開與關各比一次。

四種是 Direct JSON、Express、Elemental、Atom；後兩者原文標 EXPERIMENT、僅支援 Python。

結論是 Express 關掉思考也一樣好，實務上等於直接換到最快的推論時間。

80 倍不是 Express 單獨達成，而是改用 Jev 這類決策模型做版面決策時的降幅。

延遲降 3 倍與 token 少到 1/3，基準都是 Direct JSON，且原文都寫「最多」。

整篇數字出自 Google 自家評測，無第三方驗證。

帶走三件事

瓶頸在格式，不在協定。把模型輸出換成一行一元件，結構交給編譯器（編輯觀點）。

一個參數就能換引擎。要設計的走 Express，形狀固定的走決策模型。

倍數要連基準一起搬。3 倍對 Direct JSON，80 倍要先換 Jev，都是上限不是平均。
