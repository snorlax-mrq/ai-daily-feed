LangSmith 把治理單位從「專案」換成「代理」：一支代理一筆 record，帶負責人、不可變 ID 與類型，環境與 trace 全掛在它下面。

重組的起因：碎片化壓在兩種角色身上

原文開頭回指上週的 C 輪與新 LangSmith Agent Platform 發布，並宣告代理成為 LangSmith 各產品共同的核心物件。

原文把 2026 年定調為轉折點：新的 harness、模型與工程方法，讓代理開始能穩定做高價值的複雜工作。

結果是同一家公司裡並存多種代理：工程用 coding agent、產品做面向客戶的 agent、各團隊另有內部生產力 agent。

這些代理框架不同、跑在不同 runtime、工具與模型各異；原文的診斷是，流程因此被切碎。

原文把目標寫得很直白：生命週期要能從一個地方管完，可用任何技術棧，所有權與治理要涵蓋全部。

所以重組的目標不是再加一個功能，而是讓四段生命週期共用一個入口。

agent record：把 trace 從「專案」移到「代理」底下

舊模型是扁平專案層級：送進 LangSmith 的 trace 不屬於任何一支代理，同一支代理在 local 與 production 的 trace 也彼此無關。

原文把三項屬性講成治理前提：Owner 是具名負責人，ID 全域唯一且不可變，Type 決定資訊露出、資料連接與評測標準。

四段的分工：Build 用 Studio 的自然語言建置器、開源 harness，或任何其他框架。

Run 可部署到 Agent Server，也可留在原本的 runtime；Improve 的 tracing、evals、datasets、annotation 與 Engine，只要代理送 trace 就能用。

Govern 交給 agent registry 與 LLM Gateway，做組織層的能見度與管制。

原文說 LangSmith 可組合：代理已在別的平台上跑，接進來只做 improve 與 govern；但只接部分功能拿到的是單一入口，建與跑都在 LangSmith 才有產品加乘。

每個 trace、環境與部署都釘在同一支代理上，治理才有依附對象；原文用「每個環境與產出物都掛在同一個 agent id」收束這一段。

若建與跑都在 LangSmith，還有連鎖效果：Engine 可先用 Agent Server 的 preview 驗證修正，再合併進 production。

type 決定看什麼，OTLP 決定收得到誰

不同代理要用不同尺規：原文舉例，coding agent 看程式碼有沒有被 merge，客服 agent 則要求低延遲。

本站整理原文對三種類型的描述；原文未給這張對照表，狀態欄依原文「已提供」與「只在規劃中」的直述。

儀表板刻意帶立場：指派類型後就緒，不必先建自訂檢視；同類型量法一致，三個人跑 coding agent 也能互比。

類型是寫進架構的，不是報表上的標籤；每種代理因此自帶該看的指標與該接的資料源。

這份清單會繼續長：原文說每多一種需要專屬評測的代理，就補上對應的整合與分析。

治理那頭，原文說代理蔓延有三個來源：工程自建、事業單位採購（IT 的 ServiceNow、企業搜尋的 Glean）、員工自己撿工具。

要求全公司統一一個平台並不現實，所以改成接入即登記：支援 OTLP 的代理接上後，與自建代理同尺規量測。

成本與品質指標按環境匯總到各代理；Glean 代理成本飆高時，有名有姓的 owner 加 trace 細節可查。

原文勾勒的方向：Engine 對代理做 red team、找出失敗，並在修正上線後盯回歸；審過的案例自動流進 eval datasets。

表現最好的執行軌跡則成為微調資料，用來壓成本、拉高效能；這些零件今天都在，差的是把它們接起來。

新版已在 cloud、BYOC 與自架環境上線；最快起手是用 Studio 建第一支代理，或接上你已經在跑的代理。

路線圖上還有 org 級儀表板（目前只到 workspace 層）、把代理註冊進 IdP 供安全團隊稽核，以及 voice 類型。

帶走三件事

治理先問誰擁有，再問有幾支。沒有具名 owner，成本一飆高就沒人能答。

用類型固定量法，跨團隊才比得動。自訂儀表板只會讓數字失去可比性。

別逼全公司換平台，改成接入即登記。OTLP 是可執行治理的最小公約數。
